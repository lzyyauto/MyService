# 项目现状与后续开发路线

本文是 Z 收集系统的长期开发入口，用于回答三个问题：

1. 项目现在能做什么、不能做什么；
2. 后续应该优先解决什么；
3. 开始开发前还需要阅读哪些规范。

面向使用者的安装、启动和 API 使用方式以根目录
[`README.md`](../../README.md) 为准；代码分层与功能开发路径见
[`后端技术路线与开发规范.md`](后端技术路线与开发规范.md)；测试边界与验收要求见
[`测试规范.md`](测试规范.md)。

## 1. 当前项目定位

Z 收集系统是一个仅包含后端的个人数据收集服务，由两个相互独立的运行单元组成：

```text
客户端
  -> FastAPI
  -> HTTP Bearer API Key
  -> PostgreSQL
  -> 可选 Notion 同步
  -> 同步失败时可选 Bark 提醒

iOS 快捷指令 Notion 页面 JSON
  -> 认证的统一采集 API
  -> PostgreSQL 采集事件 / 可选业务投影
  -> 独立 Notion 投递 worker

飞书文本消息
  -> 独立 WebSocket worker
  -> 本地 Markdown
  -> 飞书 OK 回执
```

FastAPI 和飞书 worker 共用代码仓库、配置体系和 Docker 镜像，但不在同一个进程中
运行。任一侧故障不应阻塞另一侧。

## 2. 已实现能力

### 2.1 睡眠记录 API

- 记录睡眠或起床时间；
- 可选记录 WiFi、经纬度和城市；
- 未指定记录类型时，使用北京时间、上一条 `rest_time` 和 12 小时重锚定窗口自动判定；不足 2 分钟的自动重复打卡返回 `409`；
- 按当前用户查询记录并分页；
- 生成年度统计和年度明细；
- 使用数据库中的 API Key 进行 Bearer 认证；
- 配置完整时异步同步到 Notion，最终失败时可通过 Bark 提醒。

当前业务 API 只有：

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/rest-records/` | 创建睡眠或起床记录 |
| `GET` | `/api/v1/rest-records/` | 查询当前用户的记录 |
| `GET` | `/api/v1/rest-records/annual-summary/{year}` | 查询年度统计 |
| `GET` | `/api/v1/rest-records/annual-summary/{year}/table` | 查询年度明细 |

### 2.2 飞书灵感采集

- 使用飞书 WebSocket 长连接接收文本消息；
- 在回调中完成校验、进程内去重和入队；
- 后台线程按 `- [HH:MM:SS] 内容` 追加到 Markdown；
- 落盘成功后给原消息添加 `OK` reaction；
- 最近 2,000 个消息 ID 在进程内去重；
- 默认写入 `data/inspirations.md`。

### 2.3 Notion 统一采集与运动映射

- `POST /api/v1/notion-ingest/` 接收标准 Notion 页面 JSON；数据库是唯一可信数据源；
- 每次成功接收都会保存原始事件和持久化投递任务；未映射的 database ID 也会同步 Notion；
- `notion_database_mappings` 将同一用户的 database ID 关联到业务类型、显示名称和说明；
- 首个业务类型是 `exercise`，按 Notion 选项 ID 映射后严格投影为 `sport_record`；格式不符返回 `422`，
  不创建事件也不投递；
- `notion-delivery` 独立 worker 每项最多重试三次，最终失败保留证据并可通过 Bark 提醒。

具体输入契约、字段与迁移边界见
[`docs/Notion统一采集与运动映射/README.md`](../Notion统一采集与运动映射/README.md)。

### 2.4 有意保留但不开放的历史能力

GTD、Telegram 下载、视频处理和旧 AI 客户端已废弃：

- 主应用不得导入、注册或调用这些功能；
- 对应 HTTP 路径应保持 `404`；
- 历史端点即使被误注册，也必须由统一保护返回 `410`；
- 历史模型和 Alembic 迁移暂时保留，以保护已有数据库；
- 飞书灵感采集是当前有效能力，不属于已废弃的 Telegram 功能；
- 项目当前没有 AI 灵感整理能力，不得复用废弃的 `ai_client.py` 冒充实现。

## 3. 当前运行与数据边界

| 对象 | 存储位置 | 是否进入 Git | 维护要求 |
|---|---|---|---|
| 睡眠和用户数据 | PostgreSQL | 否 | 变更前备份，使用迁移演进 |
| 灵感 Markdown | `data/inspirations.md` | 否 | 部署时持久化并备份 |
| 应用配置和密钥 | `.env`/环境变量 | 否 | 不复制历史密钥，不写入文档和测试 |
| 模型结构 | `app/models/` | 是 | 与 Schema、迁移和测试同步 |
| 历史迁移 | `alembic/versions/` | 是 | 不改写已发布迁移 |

目前没有创建用户或签发 API Key 的公开 HTTP 接口。调用睡眠 API 前，必须由受控的
初始化或运维流程在 `users` 表中准备用户和唯一 `api_key`。不要把功能测试中的固定
测试 Key 用于任何真实环境。

## 4. 已知技术债

以下项目属于当前事实，不应在普通功能开发中顺手修改：

1. Alembic 已由 `20260902_notion_ingest` 合并为一个 head，但生产数据库尚未在备份副本
   上验证 upgrade/rollback；不得重置或改写历史迁移。
2. 功能测试会在空库执行 `alembic upgrade head`，但尚未在包含历史数据的生产备份副本
   上验证 upgrade/rollback；不得把空库成功等同于生产迁移链路健康。
3. 部分 Pydantic Schema 仍使用 v1 兼容写法，会产生弃用警告。
4. `rest_records.py` 同时包含 HTTP 编排、Notion 调度和年度统计，职责偏重，后续新增
   统计能力前应先拆出独立服务。
5. 飞书去重仅保存在进程内，进程重启后可能再次处理重放事件。
6. 灵感格式只有时间没有日期，不适合作为长期、跨日的结构化数据源。
7. PostgreSQL `zrest` 存在 collation 版本提示，处理前需要备份并评估索引重建。
8. 当前没有强制静态检查、CI、依赖漏洞扫描和密钥扫描。

## 5. 后续开发路线

优先级按“先保护数据和交付链路，再扩展功能”排列。每一项都应单独建立
`docs/<需求名称>/README.md`，遵循 [`docs/SETP.md`](../SETP.md)。

### P0：建立可靠的数据库迁移基线

目标是让“从受支持的生产 revision 升级到最新版本”可以被验证。

步骤：

1. 备份真实数据库，并只读确认 `alembic current`、现有表和合并 revision 的实际关系；
2. 记录生产数据库来源和可回退点；
3. 在生产数据副本上验证合并 revision 的 upgrade 和 rollback 策略；
4. 默认启用 `STRICT_MIGRATIONS=1`，并在 CI 中保留空库迁移验证。

完成标准：空库迁移和受支持旧 revision 升级均由自动化测试验证。

### P1：建立持续集成与静态质量门禁

步骤：

1. 在 CI 中执行 `./scripts/test.sh all`；
2. 引入 Ruff 或等价工具，并先以当前代码可接受的最小规则集落地；
3. 加入依赖漏洞扫描和密钥扫描；
4. 规定主分支合并前必须通过单元测试、功能测试、迁移检查和差异检查。

完成标准：本地统一入口与 CI 使用同一组命令，没有只在个人机器上存在的隐性步骤。

### P1：拆分睡眠业务逻辑

年度配对与统计算法继续增长前，建议将纯业务逻辑移入新的
`app/services/rest_records.py`，端点只负责依赖注入、参数校验和响应编排。

步骤：

1. 先用现有行为的特征测试固定配对、跨年、缺失记录和异常序列；
2. 提取不依赖 FastAPI 和数据库的纯函数；
3. 提取查询与创建用例，明确事务边界；
4. 保持 URL、状态码和响应 Schema 不变；
5. 通过现有 HTTP 功能测试确认兼容。

完成标准：端点层不再承载复杂统计计算，业务算法可以脱离数据库进行快速单元测试。

### P2：升级 Pydantic 写法

作为独立兼容性需求，把 `@validator`、类式 `Config` 和相关序列化写法迁移为 Pydantic
2 原生形式。升级前后必须对比 OpenAPI 和响应序列化，不能只以“警告消失”为完成标准。

### P2：增强飞书灵感可靠性

建议先解决可靠输入，再开发任何 AI 整理能力：

1. 增加日期或结构化事件存储，制定旧 Markdown 兼容方案；
2. 将去重状态持久化，明确消息重放语义；
3. 分离“已落盘但回执失败”和“落盘失败”的重试策略；
4. 增加文件备份、容量和写入失败监控；
5. 在稳定输入之上，另立需求设计 AI 整理能力，不启用废弃 AI 模块。

### P3：运维与可观测性

- 建立数据库和 `data/` 的备份、恢复演练；
- 为 API、Notion 同步和飞书 worker 增加结构化日志和关键指标；
- 增加并发写入、查询性能、故障注入和长时间稳定性测试；
- 评估 CORS 白名单、API Key 轮换和最小权限。

## 6. 每项需求的固定交付流程

```text
确认现状和不可破坏行为
  -> 在 docs/<需求名称>/ 写设计
  -> 先补对应层级的测试
  -> 按分层路径实现
  -> 运行 unit
  -> 运行相关 functional
  -> 涉及数据库时验证 migration
  -> 更新 README / 指南 / AGENTS.md
```

设计阶段必须明确：

- 要修改的模块和不修改的模块；
- API、数据库、文件和外部服务的兼容边界；
- 单元测试与功能测试分别验证什么；
- 数据迁移、回退和故障处理方式；
- 文档所写的是“当前实现”还是“后续计划”。
