# 测试规范

本文规定 Z 收集系统的测试分层、隔离边界、用例设计和修改后的验证要求。目标不是追求
测试数量，而是让失败能够准确指出受影响的功能，并保证每次修改不会意外触碰用户数据、
外部服务或已废弃功能。

## 1. 测试目标

每次修改至少要证明：

1. 新增或修改的业务规则符合预期；
2. API、数据库、文件或外部协议的边界保持正确；
3. 未修改的核心功能没有被意外破坏；
4. 测试环境与真实用户数据完全隔离；
5. 已废弃功能没有被重新注册或调用；
6. 数据库结构变化具备明确的升级和回退验证。

统一入口：

```bash
./scripts/test.sh unit
./scripts/test.sh functional
./scripts/test.sh all
```

不要用个人记忆拼接一组 pytest 命令作为交付标准。可以在开发时运行单个用例提高速度，
最终仍要运行与改动范围匹配的统一入口。

## 2. 测试金字塔

| 层级 | 目录 | 验证内容 | 允许的依赖 | 运行速度 |
|---|---|---|---|---|
| 单元测试 | `tests/unit/` | 单个函数、服务、Schema、端点编排 | mock、fake、临时目录 | 快 |
| 功能测试 | `tests/functional/` | 真实 HTTP、PostgreSQL、文件、跨组件协议 | 一次性容器、本地替身 | 较慢 |
| 人工冒烟 | 不进入默认自动化 | 真实飞书长连接、真实 Notion/Bark 授权 | 受控测试账号 | 按需 |
| 生产迁移验证 | 待补齐 | 受支持 revision 的升级/回退 | 脱敏数据副本 | 发布前 |

自动化用例应尽量下沉到最便宜的层级。纯算法错误由单元测试定位，只有依赖真实协议、
数据库行为或多个组件协作的内容才进入功能测试。

## 3. 单元测试规范

### 3.1 边界

单元测试必须：

- 不要求 Docker；
- 不访问网络；
- 不连接 PostgreSQL 或任何真实数据库；
- 不读取正式 `.env` 中的凭证来调用外部服务；
- 不写入 `data/` 或用户文件；
- 使用 `tmp_path` 处理文件；
- 使用 `MagicMock`、`AsyncMock`、fake 或纯内存对象替代边界依赖；
- 用例之间不共享可变状态，能够独立、乱序运行。

### 3.2 当前覆盖范围

当前单元测试负责验证：

- Schema、时区转换和字段约束；
- Bearer 认证成功、缺失和非法 Key；
- 睡眠记录首次默认值和自动切换；
- 列表过滤、排序和分页编排；
- 年度配对和核心统计；
- Notion 数据格式、重试和 Bark 失败提醒；
- 飞书文本过滤、去重、落盘顺序、token 缓存和 reaction；
- 活跃路由白名单、OpenAPI 范围和废弃路由保护；
- 所有当前及兼容模型均已注册到 SQLAlchemy metadata。

### 3.3 用例编写方式

每个行为至少包含适用的三类用例：

- 正常路径：有效输入得到预期输出；
- 边界路径：空值、上下限、跨日/跨年、缺失配对或重复事件；
- 失败路径：认证失败、外部服务失败、非法响应、文件写入失败。

用例名称描述行为和结果，例如：

```python
def test_schedule_sync_skips_when_notion_is_not_configured():
    ...
```

避免名称只写 `test_create_1` 或测试函数内部实现细节。

### 3.4 Mock 原则

- 在被测模块实际查找对象的位置打补丁；
- 只 mock 网络、时间、随机值、数据库和文件等边界；
- 不要把整个被测函数 mock 掉；
- 对关键副作用同时断言“发生”和“没有发生”；
- 异步调用使用 `AsyncMock` 并通过 `assert_awaited*` 验证；
- 时间相关逻辑使用固定时间戳，不依赖执行当天的偶然结果。

### 3.5 覆盖率

`./scripts/test.sh unit` 当前统计以下活跃模块：

- `app.api.v1.endpoints.rest_records`
- `app.core.security`
- `app.services.inspiration`
- `app.services.notion`
- `app.services.bark`

行覆盖率门槛为 75%。废弃兼容函数不计入门槛。

覆盖率是兜底门槛，不是完成标准。新增复杂分支必须有行为断言；不能通过
`pragma: no cover`、空断言或仅执行代码来规避。新增活跃模块后，应同步把它加入
`scripts/test.sh` 的覆盖率范围。

## 4. 功能测试规范

### 4.1 环境

`./scripts/test.sh functional` 使用 `docker-compose.functional.yml`：

- 构建与生产相同 Dockerfile 的 FastAPI 镜像；
- 启动一次性 PostgreSQL 15；
- 使用唯一 Compose 项目名；
- PostgreSQL 数据目录使用 tmpfs；
- 默认映射 API 端口 `18080`、数据库端口 `15432`；
- 测试结束执行 `down --volumes --remove-orphans`。

端口冲突时：

```bash
FUNCTIONAL_TEST_PORT=28080 FUNCTIONAL_TEST_DB_PORT=25432 \
  ./scripts/test.sh functional
```

仅调试失败现场时：

```bash
KEEP_TEST_STACK=1 ./scripts/test.sh functional
```

使用 `KEEP_TEST_STACK=1` 后，开发者负责手工清理对应容器和数据。不得在 CI 中保留。

### 4.2 数据隔离

功能测试只能使用 Compose 中声明的：

- 数据库名、用户和密码均为 `functional`；
- 固定测试用户和 `functional-test-api-key`；
- 测试运行时创建的数据；
- 本地临时文件和本地 HTTP 替身。

禁止：

- 读取开发或生产数据库连接作为功能测试目标；
- 使用真实用户 API Key；
- 请求真实飞书、Notion 或 Bark；
- 把测试结果写入项目的 `data/`；
- 依赖功能测试之间的执行顺序；
- 在失败清理时删除非本次 Compose 项目的容器或卷。

### 4.3 当前覆盖范围

HTTP/PostgreSQL 功能测试验证：

- 根路径和 OpenAPI；
- 只开放当前睡眠业务端点；
- 缺失或非法认证返回 `401`；
- 非法记录类型、分页和年份返回 `422`；
- 创建睡眠和自动创建起床；
- 真实 SQLAlchemy/PostgreSQL 落库；
- 列表排序和分页；
- 年度明细配对与年度统计；
- GTD、Telegram、视频和 `/downloads` 持续返回 `404`。

飞书本地跨组件测试验证：

```text
模拟飞书事件
  -> 真实 collector
  -> 临时 Markdown
  -> 本地 token HTTP 替身
  -> 本地 reaction HTTP 替身
```

它不建立真实飞书 WebSocket，也不使用真实凭证。

### 4.4 新增功能测试的条件

出现下列变化之一，应新增或修改功能测试：

- 路由、方法、状态码、认证或响应契约变化；
- SQLAlchemy 查询或事务行为变化；
- 新表、字段、约束或迁移；
- Dockerfile、Compose、启动命令或环境变量变化；
- 文件格式、落盘路径或跨组件顺序变化；
- 第三方 HTTP 协议、超时、认证头或重试行为变化；
- 废弃功能边界变化。

功能测试应该从外部可观察接口断言结果，不直接复制内部算法。算法细节留给单元测试。

## 5. 数据库迁移测试

当前功能测试容器通过 `init_db/create_all` 在空库建表。它可以证明：

- 当前模型能够在 PostgreSQL 上建表；
- FastAPI、认证、ORM 和 HTTP 链路可运行；
- 当前查询与写入行为正确。

它不能证明：

- Alembic 历史迁移可以从空库顺序执行；
- 真实数据库能从当前 revision 升级；
- 两个 Alembic head 的关系正确；
- downgrade 不丢失数据；
- 生产数据库 collation 问题已解决。

在 Alembic 基线修复前：

```bash
STRICT_MIGRATIONS=1 ./scripts/test.sh unit
```

会把多个 head 从警告升级为失败。涉及数据库结构的需求不得仅凭当前功能测试交付，必须
在备份或脱敏副本上额外验证迁移计划。

迁移基线修复后，功能测试应改为：

1. 对空库执行 `alembic upgrade head`；
2. 检查只有一个 head；
3. 从至少一个受支持旧 revision 升级；
4. 验证关键数据和约束保留；
5. 根据迁移风险验证 downgrade 或明确的前滚恢复方案。

## 6. 按修改类型选择测试

| 修改类型 | 必须运行 | 重点新增/复核 |
|---|---|---|
| 纯文档 | `git diff --check`，核对链接和命令 | 当前事实与计划是否混淆 |
| 纯业务算法 | `./scripts/test.sh unit` | 正常、边界、失败、回归样例 |
| Schema/认证 | `./scripts/test.sh all` | 401/422、OpenAPI、响应兼容 |
| 路由/端点 | `./scripts/test.sh all` | 路由白名单、真实 HTTP |
| Model/查询 | `./scripts/test.sh all` | 真实 PostgreSQL、用户隔离 |
| Alembic | `./scripts/test.sh all` + 专项迁移验证 | upgrade、数据保留、回退 |
| Notion/Bark | `./scripts/test.sh unit`，协议变更时加本地功能替身 | 未配置、超时、重试、最终失败 |
| 飞书 collector | `./scripts/test.sh all` | 去重、落盘先于回执、错误响应 |
| worker/容器/启动 | `./scripts/test.sh all` | 独立进程、健康检查、停止行为 |
| 依赖或锁文件 | `./scripts/test.sh all` | `uv sync --locked`、生产依赖边界 |
| 废弃兼容代码 | `./scripts/test.sh unit`，涉及注册时运行 `all` | 404/410、防止主应用导入 |

如果一次修改跨越多行，按最高风险层级验证。

## 7. 保证“只影响对应功能”的方法

开发前建立影响矩阵：

| 变化点 | 直接影响 | 必须保持不变 | 对应测试 |
|---|---|---|---|
| 示例：年度配对算法 | 年度明细、年度统计 | 创建、认证、飞书 worker | 算法单元测试 + HTTP 功能测试 |

实际开发时遵循：

1. 先用现有测试或新增特征测试固定不能破坏的行为；
2. 把变更限制在对应模块，不顺手清理无关历史代码；
3. 外部服务、数据库、时间和文件均通过明确边界隔离；
4. 单元测试验证规则，功能测试验证组件连接，不重复所有断言；
5. 查看完整差异，确认没有密钥、用户数据、运行时文件或无关格式化；
6. 最后运行统一入口，而不是只运行刚新增的用例。

## 8. 测试失败处理

- 先确认失败是否由本次修改引起，不立即放宽断言；
- 测试暴露真实缺陷时修复代码，并补充能解释缺陷的最小用例；
- 需求确实改变旧行为时，先更新设计和兼容说明，再修改测试；
- 不通过删除用例、扩大 mock 范围或降低覆盖率来“修复”失败；
- 功能测试失败时检查容器日志、端口、数据库就绪和本地替身请求记录；
- Docker daemon 未运行属于环境阻塞，只能说明功能测试未执行，不能宣称全部通过。

## 9. 交付清单

交付前确认：

- [ ] 新行为有对应测试；
- [ ] 受影响的旧行为有回归测试；
- [ ] 单元测试没有网络、真实数据库或用户数据访问；
- [ ] 功能测试只使用一次性 PostgreSQL 和本地替身；
- [ ] 新活跃模块已纳入覆盖率统计；
- [ ] 废弃路径仍是 `404`，误注册保护仍是 `410`；
- [ ] 数据库变化有新 migration，未改写历史 migration；
- [ ] 已记录实际执行的命令和结果；
- [ ] 未执行的验证被明确标注，而不是写成通过；
- [ ] 容器、卷和临时文件已清理；
- [ ] README、专题文档和 `AGENTS.md` 已同步。
