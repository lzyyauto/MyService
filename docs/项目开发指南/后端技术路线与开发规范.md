# 后端技术路线与开发规范

本文描述当前后端的真实结构，以及新增或修改一个功能时应遵循的开发路径。它不是对
理想架构的虚构；文中标记为“建议”的内容需要通过独立需求逐步实施。

## 1. 技术路线

| 领域 | 当前选择 | 主要入口 |
|---|---|---|
| 运行时 | Python 3.11 | `.python-version`、`pyproject.toml` |
| HTTP API | FastAPI 0.104.1 | `app/main.py` |
| 请求/响应校验 | Pydantic 2.5.2 | `app/schemas/` |
| 数据访问 | SQLAlchemy 2.0 ORM | `app/models/`、`app/db/` |
| 数据库 | PostgreSQL 15（功能测试）/ PostgreSQL 14+（项目要求） | `docker-compose*.yml` |
| 数据库迁移 | Alembic 1.12.1 | `alembic/` |
| API 认证 | HTTP Bearer + `users.api_key` | `app/core/security.py` |
| 外部集成 | Notion、Bark、飞书开放平台 | `app/services/` |
| 后台进程 | 独立飞书 WebSocket worker | `app/workers/` |
| 依赖管理 | uv + `uv.lock` | `pyproject.toml` |
| 测试 | pytest、pytest-asyncio、pytest-cov | `tests/`、`scripts/test.sh` |
| 部署 | Docker、Docker Compose | `Dockerfile`、`docker-compose.yml` |

项目当前只有后端，没有前端工程、前端 API 适配层或用户管理界面。

## 2. 运行时结构

### 2.1 FastAPI 请求链路

```text
app/main.py
  -> 注册 app/api/v1/endpoints/rest_records.py
  -> FastAPI Depends(get_current_user, get_db)
  -> Pydantic Schema 校验输入
  -> SQLAlchemy 查询或写入 PostgreSQL
  -> Pydantic Schema 序列化响应
  -> 配置完整时调度 Notion 后台同步
  -> 最终失败时可选 Bark 通知
```

应用启动时由 lifespan 调用 `init_db()`。当前 `init_db()` 使用
`Base.metadata.create_all()`，这只能补建当前模型缺少的表，不能替代版本化迁移。
生产数据库结构演进仍应由 Alembic 管理。

### 2.2 飞书灵感链路

```text
app/workers/feishu_inspiration.py
  -> 读取 Settings
  -> FeishuInspirationCollector.run()
  -> 飞书 WebSocket 回调
  -> 校验、去重、入队
  -> 后台消费者追加 Markdown
  -> 飞书 HTTP reaction
```

worker 不得加入 FastAPI lifespan，也不得注册为 HTTP 路由。这样可避免 Uvicorn reload
或多 worker 导致重复长连接，并保证灵感采集故障不影响 API。

## 3. 模块职责与依赖方向

| 目录/文件 | 职责 | 可以依赖 | 不应承担 |
|---|---|---|---|
| `app/main.py` | 应用组装、生命周期、中间件、路由注册 | `api`、`db`、`core` | 具体业务算法 |
| `app/api/v1/endpoints/` | HTTP 参数、依赖注入、状态码、用例编排 | `schemas`、`services`、`models`、`db`、`core` | 可复用的复杂算法、长期后台循环 |
| `app/schemas/` | 输入输出结构、字段约束、序列化 | Pydantic、纯工具 | 数据库查询、外部 HTTP |
| `app/models/` | 表、字段、约束、关系 | `db.base_class`、SQLAlchemy | API 响应格式、外部集成 |
| `app/services/` | 业务用例、纯业务算法、外部系统适配 | `models`、`schemas`、`core` | 路由注册、应用启动 |
| `app/workers/` | 独立进程组装和生命周期 | `services`、`core` | 重复实现业务逻辑 |
| `app/core/` | 配置、认证、废弃保护等横切能力 | 基础设施 | 具体业务功能 |
| `app/db/` | Engine、Session、Base、初始化 | `core.config`、`models` 注册 | HTTP 语义 |
| `alembic/` | 可审计的数据库版本演进 | 模型元数据 | 普通运行时业务 |
| `scripts/` | 人工运维或统一开发入口 | 项目命令 | 被 API 隐式调用的业务逻辑 |
| `tests/unit/` | 隔离的快速行为验证 | mock/fake、纯业务代码 | 网络、真实数据库、用户数据 |
| `tests/functional/` | 跨组件和真实协议链路 | 一次性服务、本地替身 | 正式数据库和真实外部服务 |

推荐依赖方向：

```text
main / workers
  -> endpoints
  -> services
  -> models / schemas
  -> db / core
```

这是约束目标，不是当前所有历史代码都已完全达到的状态。例如
`rest_records.py` 仍包含较多统计逻辑；新增复杂逻辑时不应继续扩大该文件，而应先按
独立需求提取服务。

## 4. 功能代码应该放在哪里

| 要开发的内容 | 首选位置 | 同步检查 |
|---|---|---|
| 新 HTTP 端点 | `app/api/v1/endpoints/<领域>.py` | `app/main.py` 注册、OpenAPI、认证、功能测试 |
| 请求或响应字段 | `app/schemas/<领域>.py` | 向后兼容、422 行为、OpenAPI |
| 新表或字段 | `app/models/<领域>.py` | `app/models/__init__.py`、Alembic、迁移测试 |
| 可复用业务规则 | `app/services/<领域>.py` | 纯单元测试、端点编排 |
| 第三方 API 调用 | `app/services/<系统>.py` | 超时、错误语义、fake/mock、禁止默认真实调用 |
| 长连接或持续消费者 | `app/workers/<名称>.py` | 独立进程、停止行为、重复实例风险 |
| 认证、配置、废弃保护 | `app/core/` | 全局回归和安全边界 |
| 数据库会话和 Base | `app/db/` | 生命周期、连接释放、所有模型注册 |
| 人工诊断/运维命令 | `scripts/` | 明确副作用，不被 pytest 自动收集 |
| 需求和设计 | `docs/<中文需求名>/README.md` | `docs/SETP.md` 五阶段 |

不要因为目录中仍保留历史文件，就把新代码加入 `gtd.py`、`telegram.py`、
`video_process.py`、`video_processor.py` 或 `utils/ai_client.py`。

## 5. 开发一个功能的标准路径

### 第一步：定义边界

在 `docs/<需求名称>/README.md` 写清：

- 用户目标和验收条件；
- 当前行为与不能破坏的行为；
- API、数据库、文件、外部服务是否变化；
- 是否涉及真实数据、密钥或不可逆操作；
- 明确不在本次范围内的内容。

涉及废弃功能时，默认选择是保持不可调用，而不是恢复历史实现。

### 第二步：定位改动层

从外到内确认：

1. 是否需要新增或改变路由；
2. 输入输出 Schema 是否变化；
3. 是否有可独立测试的业务规则；
4. 模型和数据库结构是否变化；
5. 是否调用外部系统；
6. 是否需要独立 worker，而不是挂入 API 进程。

如果一个业务规则不需要知道 FastAPI、SQLAlchemy Session 或网络客户端，应优先写成
服务中的纯函数。

### 第三步：先定义测试影响面

至少列出：

- 正常路径；
- 边界和非法输入；
- 当前用户数据隔离；
- 外部服务未配置、超时和失败；
- 与已有功能的回归边界；
- 数据库变更的升级和回退；
- 废弃路由仍保持不可访问。

测试层级选择见 [`测试规范.md`](测试规范.md)。

### 第四步：实现最小闭环

通常按以下顺序修改：

```text
Schema
  -> 纯业务规则 / Service
  -> Model 与 Migration（如需要）
  -> Endpoint 或 Worker
  -> 应用组装
  -> 单元测试
  -> 功能测试
  -> 文档
```

顺序可以因功能调整，但不得只改端点而漏掉 Schema、迁移、测试或文档。

### 第五步：验证与交付

无数据库和外部链路变化的最小验证：

```bash
./scripts/test.sh unit
```

API、数据库、容器或跨组件链路变化：

```bash
./scripts/test.sh all
```

涉及数据库结构时，还必须确认：

```bash
uv run alembic heads
uv run alembic current
```

在两个 head 的已知问题解决前，不得把 `create_all` 功能测试当作迁移验证。最终交付应
记录测试结果、已知限制、数据影响和回退方式，并更新 `AGENTS.md`。

## 6. 代码规范

### 6.1 Python 基本规则

- 使用 Python 3.11 语法，新增代码提供类型标注；
- 文件、函数和变量使用 `snake_case`，类使用 `PascalCase`，常量使用
  `UPPER_SNAKE_CASE`；
- 导入按标准库、第三方、项目内部三组排列；不使用通配符导入；
- 函数保持单一职责，复杂分支拆成有名字的辅助函数；
- 注释解释“为什么”和兼容约束，不复述代码表面行为；
- 面向用户、日志和项目文档使用中文；第三方协议字段保留其官方名称；
- 新增公共函数、服务和复杂算法应有简短 docstring；
- 不在模块导入阶段启动网络连接、线程或真实外部写入；
- 日志使用 `logging`，不使用 `print` 输出运行时业务信息；
- 不记录 API Key、数据库密码、飞书密钥、Notion token 或完整敏感载荷。

项目当前尚未配置 Ruff 等自动格式门禁，所以这些规则需要代码审查和测试共同保证。
引入自动工具应作为独立需求，避免一次性格式化掩盖业务差异。

### 6.2 API 规则

- 业务端点默认使用 `get_current_user`，公开端点必须在设计中明确理由；
- 通过 Pydantic/`Query`/`Path` 在入口处约束参数；
- 使用 `response_model` 固定输出契约；
- 认证失败保持 `401`，参数校验失败保持 `422`；
- 列表查询必须按当前用户过滤，并设置合理分页上限；
- API 路径、状态码或字段的破坏性变化必须有版本或迁移策略；
- 新路由注册后同步更新路由白名单和 OpenAPI 功能测试；
- 不注册已废弃路由，不挂载 `/downloads`。

### 6.3 数据库规则

- 所有 Session 通过 `get_db()` 或明确的受控生命周期获取并关闭；
- 写操作明确 `commit`、失败处理和外部副作用顺序；
- 外部 API 失败不得回滚已经成功提交的核心睡眠记录；
- 表结构变化必须新增 Alembic revision，不改写已发布 revision；
- 新模型必须在 `app/models/__init__.py` 注册；
- 删除表、列或历史模型前先备份并设计兼容迁移；
- 不以 `create_all` 代替生产迁移；
- 测试不得连接 `.env` 指向的真实数据库。

### 6.4 外部服务规则

- Notion、Bark、飞书调用统一放在服务层；
- 凭证缺失时，可选集成应安全跳过或在独立 worker 启动时明确失败；
- 每个 HTTP 调用必须设置超时；
- 明确重试次数、可重试错误、幂等性和最终失败行为；
- 单元测试使用 mock，功能测试使用本地替身；
- 自动化测试不得请求真实 Notion、Bark 或飞书；
- 文件必须落盘成功后才能发送飞书成功回执。

### 6.5 并发和后台任务规则

- FastAPI 后台任务只承载短时、可丢失且不影响核心事务的附加工作；
- 长连接、永久循环和独立消费队列放入 `app/workers/`；
- Uvicorn reload 或多进程环境下必须评估重复执行；
- 内存去重不能宣称为跨重启幂等；
- 新增后台任务必须记录异常，且不得吞掉核心请求错误。

## 7. 配置与依赖规范

- 有效配置只在 `app/core/config.py` 的 `Settings` 中声明；
- 新配置同步更新 `.env.example`、README、Docker/Compose 和测试环境；
- `.env.example` 只放安全占位符；
- 生产依赖使用 `uv add`，测试依赖使用 `uv add --dev`；
- 废弃能力依赖留在 `legacy` 组，普通开发和 Docker 不安装；
- `pyproject.toml` 与 `uv.lock` 必须一起提交；
- 不提交 `.env`、`.venv/`、`data/` 和用户运行数据。

## 8. 文档规范

- 新需求使用中文目录 `docs/<需求名称>/`；
- 按“现状、设计、实施、验证、交付”维护；
- 当前事实与未来建议分开书写；
- 命令必须来自仓库的真实统一入口；
- 变更完成后更新根 README、相关专题文档和 `AGENTS.md`；
- 如果实现偏离设计，记录偏差原因和影响，不能只修改结论。
