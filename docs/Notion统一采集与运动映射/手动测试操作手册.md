# Notion 统一采集：本地手动测试手册

本文只验证本地运行的 FastAPI、PostgreSQL、Notion 投递 worker 和真实 Notion 表，不使用
Docker。Docker/Compose 的部署与验证属于下一阶段，不是本轮测试前提。

本轮只验证两条最小业务路径：

| 路径 | 已有条件 | 本地结果 | Notion 结果 |
|---|---|---|---|
| 已确认的运动业务 | 已有正式运动表，快捷指令 JSON 与其字段一致 | 保存原始事件，并写入 `sport_record` | 异步转发到原运动表 |
| 未确认业务的普通表 | 已有一张转发请求测试表，不建立映射 | 只保存一条原始 JSON 事件，不写任何业务表 | 异步转发到测试表 |

这里的“只保存一条原始事件”还会配套产生一条 `notion_deliveries` 技术记录，用于保存重试
状态。它不是第二份业务数据。

## 1. 通过标准

满足以下结果即可证明当前设计可行：

1. 运动请求返回 `202`，本地同时出现一条采集事件、一条运动业务记录和一条投递任务；
2. worker 把运动投递任务更新为 `succeeded`，原运动 Notion 表出现新页面；
3. 未映射测试请求返回 `202`，本地只有采集事件和投递任务，没有运动业务记录；
4. worker 把测试投递任务更新为 `succeeded`，转发测试表出现新页面；
5. 已映射的运动请求如果字段解析失败，直接返回 `422`，本地和 Notion 都不新增数据。

幂等验证是建议项：相同 `idempotency_key` 重发时应返回 `duplicate: true`，不重复写入或
转发。

## 2. 已知边界

### 2.1 运动本地表是固定业务结构

当前系统已经按现有运动 Notion 载荷建立 `sport_record`，不是根据每个请求动态创建 SQL
表。字段关系如下：

| Notion property | 本地字段 | 规则 |
|---|---|---|
| `运动类型.select.id` | `sport_type` | 必填；按 `notion_select_option_mappings.option_id` 查得 `name` 后写入。`select.name` 与 `select.color` 忽略；未知 ID 返回 `422` |
| `时长.number` | `duration` | 必填非负数字，业务单位固定为分钟 |
| `记录时间.date.start` | `occurred_at` | 必填 ISO 8601 时间且带时区 |
| `日期.date.start` | `occurred_on` | 必填 `YYYY-MM-DD` |
| `月份.title` | `month_str` | 必填非空文本 |
| `城市.rich_text` | `city` | 可选 |

其他 Notion 字段仍保存在原始 JSON 中并转发给 Notion，但不会自动变成
`sport_record` 的列。

### 2.2 普通表以后可以业务化，但不追溯历史

未映射时，系统不理解测试表的业务含义，只做原始 JSON 留存和 Notion 转发。以后如果为该
database ID 建立了某个业务映射，映射只处理建立映射之后的新请求；此前保存的历史 JSON
不自动回填业务表，也不要求迁移。

## 3. 测试前准备

在项目根目录 `/Users/zingliu/Code/my-service` 操作。

### 3.1 本地环境

需要：

- Python 3.11 和 `uv`；
- 一套已经运行的本地 PostgreSQL；
- `.env` 中的 PostgreSQL 配置能够连接这套数据库；
- 现有系统 API Key；
- 真实可用的服务器端 `NOTION_TOKEN`。

首次同步依赖：

```bash
uv sync --locked
```

确认 `.env` 至少满足：

```env
ENABLE_PUBLIC_REQUEST_DUMP=false
NOTION_TOKEN=<服务器端 Notion Token>
```

快捷指令不能继续携带 Notion Token。此前出现在公开调试日志中的 Token 应先在 Notion
撤销并重新生成。新的 Token 只保存在本地 `.env`。

FastAPI 启动时会通过 `Base.metadata.create_all()` 补建缺少的本地表，不会删除已有表；如果
此前本地已存在旧版 Notion 映射、事件、运动或投递表，启动时还会补齐本需求所需列并保留
原有行。这足够用于本轮本地功能验证，但不代表生产 Alembic 升级已经验证。

### 3.2 两张已经存在的 Notion 表

不需要再创建新的运动测试表。本轮直接使用：

1. **现有运动表**：已有运动字段，记下其 database ID 为
   `<EXERCISE_DATABASE_ID>`；
2. **转发请求测试表**：不确认业务、不建立映射，记下其 database ID 为
   `<FORWARD_TEST_DATABASE_ID>`。

将 `.env` 中 `NOTION_TOKEN` 对应的 Notion integration 分享给这两张表，否则 worker 会
投递失败。测试表的 property 名称和类型以它自己的实际结构为准。

## 4. 启动本地进程

需要三个终端。

### 终端 A：启动 API

```bash
cd /Users/zingliu/Code/my-service
uv run uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

启动时没有数据库连接或建表错误后，在终端 C 验证：

```bash
curl -i http://127.0.0.1:8000/
```

预期为 `200 OK`，正文包含 `欢迎使用 Z 收集系统 API`。

### 终端 B：启动 Notion 投递 worker

```bash
cd /Users/zingliu/Code/my-service
uv run python -m app.workers.notion_delivery
```

worker 空闲时可能没有日志。是否投递成功以数据库中的 `notion_deliveries.status` 和 Notion
页面为准。

### 终端 C：发送请求和只读检查

后续所有 `curl` 和数据库检查都在这个终端执行。将文档中的占位符替换为实际值：

- `<SYSTEM_API_KEY>`：现有系统 API Key，不是 Notion Token；
- `<EXERCISE_DATABASE_ID>`：现有运动表的 database ID；
- `<FORWARD_TEST_DATABASE_ID>`：转发请求测试表的 database ID。

## 5. 路径一：运动业务入库并转发

### 5.1 建立运动映射

只需配置一次。它把现有运动 Notion 表标记为本地 `exercise` 业务：

```bash
curl -i -X PUT \
  'http://127.0.0.1:8000/api/v1/notion-ingest/mappings/<EXERCISE_DATABASE_ID>' \
  -H 'Authorization: Bearer <SYSTEM_API_KEY>' \
  -H 'Content-Type: application/json' \
  -d '{
    "business_type": "exercise",
    "display_name": "日常运动记录",
    "description": "现有 iOS 运动快捷指令对应的业务表；字段按 exercise_notion_v1 解析。"
  }'
```

预期 `200 OK`。确认映射存在：

```bash
curl -i \
  'http://127.0.0.1:8000/api/v1/notion-ingest/mappings' \
  -H 'Authorization: Bearer <SYSTEM_API_KEY>'
```

预期列表中只有需要业务化的 database 才有映射；转发测试表不应出现在列表里。

### 5.2 提交现有运动 JSON

优先使用现有快捷指令实际生成的 `parent` 和 `properties`，只做三项改动：

1. URL 改为 `http://<本机局域网 IP>:8000/api/v1/notion-ingest/`；
2. Authorization 改为 `Bearer <SYSTEM_API_KEY>`；
3. 顶层增加本次请求唯一的 `idempotency_key`。

也可以先用下面的 curl。`运动类型.select` 的内容应替换为现有运动表中的真实选项；其余
property 名称和类型不要改：

```bash
curl -i -X POST \
  'http://127.0.0.1:8000/api/v1/notion-ingest/' \
  -H 'Authorization: Bearer <SYSTEM_API_KEY>' \
  -H 'Content-Type: application/json' \
  -d '{
    "parent": {
      "type": "database_id",
      "database_id": "<EXERCISE_DATABASE_ID>"
    },
    "properties": {
      "运动类型": {
        "type": "select",
        "select": {"name": "<现有运动类型选项>"}
      },
      "月份": {
        "type": "title",
        "title": [{"type": "text", "text": {"content": "09月"}}]
      },
      "城市": {
        "type": "rich_text",
        "rich_text": [{"type": "text", "text": {"content": "上海市"}}]
      },
      "时长": {"type": "number", "number": 1},
      "记录时间": {
        "type": "date",
        "date": {"start": "2026-09-16T20:00:00+08:00"}
      },
      "日期": {"type": "date", "date": {"start": "2026-09-16"}}
    },
    "idempotency_key": "manual-exercise-20260916-001"
  }'
```

预期 `202 Accepted`，响应中：

```json
{
  "business_type": "exercise",
  "mapping_name": "日常运动记录",
  "delivery_status": "pending",
  "duplicate": false
}
```

保留响应中的 `event_id` 和 `delivery_id`。worker 默认几秒内开始投递；随后执行第 7 节的
本地检查，并在原运动 Notion 表确认新增页面。

## 6. 路径二：未知业务只留存并转发

不要为 `<FORWARD_TEST_DATABASE_ID>` 建立映射。请求的 `properties` 必须严格采用转发测试表
自己的真实 property 名称和 Notion 类型。下面假设它有一个 Title 字段叫“名称”；如果你的
测试表标题字段名不同，只替换“名称”：

```bash
curl -i -X POST \
  'http://127.0.0.1:8000/api/v1/notion-ingest/' \
  -H 'Authorization: Bearer <SYSTEM_API_KEY>' \
  -H 'Content-Type: application/json' \
  -d '{
    "parent": {
      "type": "database_id",
      "database_id": "<FORWARD_TEST_DATABASE_ID>"
    },
    "properties": {
      "名称": {
        "type": "title",
        "title": [{
          "type": "text",
          "text": {"content": "本地转发测试 2026-09-16"}
        }]
      }
    },
    "idempotency_key": "manual-forward-20260916-001"
  }'
```

预期 `202 Accepted`，并且：

```json
{
  "business_type": null,
  "mapping_name": null,
  "delivery_status": "pending",
  "duplicate": false
}
```

随后应看到：

- `notion_ingest_events` 新增一条，`original_payload` 保存完整 JSON；
- `notion_deliveries` 新增一条，并最终变为 `succeeded`；
- `sport_record` 没有这次请求对应的记录；
- 转发测试 Notion 表新增页面。

## 7. 不依赖 Docker 的本地数据库检查

下列命令只读取当前 `.env` 指向的 PostgreSQL，不打印数据库密码。它显示最近的采集事件、
运动记录和投递状态：

```bash
uv run python - <<'PY'
from sqlalchemy import select

from app.db.session import SessionLocal
from app.models.notion_ingest import NotionDelivery, NotionIngestEvent, SportRecord

with SessionLocal() as db:
    print("\n最近采集事件")
    events = db.execute(
        select(
            NotionIngestEvent.id,
            NotionIngestEvent.notion_database_id,
            NotionIngestEvent.business_type,
            NotionIngestEvent.mapping_display_name,
            NotionIngestEvent.idempotency_key,
        ).order_by(NotionIngestEvent.created_at.desc()).limit(10)
    ).all()
    for row in events:
        print(row)

    print("\n最近运动业务记录")
    records = db.execute(
        select(
            SportRecord.source_event_id,
            SportRecord.sport_type,
            SportRecord.duration,
            SportRecord.occurred_at,
            SportRecord.occurred_on,
            SportRecord.city,
        ).order_by(SportRecord.created_at.desc()).limit(10)
    ).all()
    for row in records:
        print(row)

    print("\n最近 Notion 投递")
    deliveries = db.execute(
        select(
            NotionDelivery.event_id,
            NotionDelivery.status,
            NotionDelivery.attempt_count,
            NotionDelivery.notion_page_id,
            NotionDelivery.last_error,
        ).order_by(NotionDelivery.created_at.desc()).limit(10)
    ).all()
    for row in deliveries:
        print(row)
PY
```

重点用 POST 响应中的 `event_id` 对照：

- 运动 `event_id` 应同时出现在三组结果中；
- 转发测试 `event_id` 只应出现在“最近采集事件”和“最近 Notion 投递”中；
- 成功后 `status` 为 `succeeded`，`attempt_count` 通常为 `1`，并有
  `notion_page_id`。

如果刚提交时仍是 `pending`，确认终端 B 的 worker 仍在运行，稍后再次执行检查命令。

## 8. 建议补充验证

### 8.1 幂等

原样重发第 5 或第 6 节的请求，保持同一个 `idempotency_key`。预期仍为 `202`，但
`duplicate` 为 `true`，三张本地表和 Notion 都不新增记录。

### 8.2 已映射请求解析失败

复制运动请求，换一个新的 `idempotency_key`，并把 `时长.number` 改成 `-1`。预期：

- HTTP 返回 `422`；
- 不创建采集事件；
- 不创建运动记录；
- 不创建投递任务；
- Notion 不新增页面。

这条规则只适用于已经映射的业务请求。未映射请求只验证基础 Notion 页面结构，具体属性能
否被目标表接受由 Notion API 决定。

## 9. 故障定位

| 现象 | 首先检查 |
|---|---|
| API 启动时报数据库错误 | 本地 PostgreSQL 是否运行；`.env` 的 host、port、database、user 是否正确 |
| `401` | 使用的是否为系统 API Key，而不是 Notion Token |
| 运动请求 `422` | 六个运动 property 的名称、type 和内容是否符合第 2.1 节 |
| 测试转发最终失败 | 测试表的标题字段名/type 是否匹配；integration 是否已分享给该表 |
| 一直是 `pending` | 终端 B 的 `notion_delivery` worker 是否运行；`.env` 是否有 `NOTION_TOKEN` |
| 最终为 `failed` | 查看 `last_error`；worker 最多重试三次，原始事件仍会保留 |
| Notion 页面重复 | 快捷指令同一次逻辑请求的重试是否复用了同一个 `idempotency_key` |

本轮测试不需要运行 `docker compose`，也不需要执行 Docker 功能测试。等这两条真实链路都
通过后，再单独讨论容器部署、数据卷、健康检查和生产迁移验证。
