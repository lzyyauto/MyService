# 飞书业务扩展与重启规则

> **历史文档，已停止实施。** 2026-10-02 按新需求撤回 AI 整理、每日调度与结果投递。
> 下文保留此前设计，仅供追溯，命令和配置不适用于当前版本。
> 当前运行、来源 ID 查询和扩展请用[纯采集操作手册](../飞书采集职责简化/操作手册.md)；
> 决定见[职责简化说明](../飞书采集职责简化/README.md)。

适用：已经使用 `config/feishu.toml` 的新版采集与整理角色。
同一个机器人新增群聊分流、Markdown 收集流程或 AI 提示词，通常只改配置，自动热加载。
不需要重启 FastAPI、前端或整个项目，也不需要重建 Docker 镜像。

## 1. 先确定增加的是哪一层

| 对象 | 定义内容 | 什么情况下增加 |
|---|---|---|
| apps | 飞书机器人连接、凭证变量名、默认流程 | 新建另一个飞书机器人 |
| routes | 哪个应用／会话进入哪个流程 | 新群分流、群聊或私聊类型分流、可选用户／@ 过滤 |
| pipelines | 收集文件、处理器、AI、提示词、结果路径和投递位置 | 不同业务需要独立原文、提示词或结果 |
| ai_profiles | Base URL、模型、超时、参数和密钥变量名 | 使用另一套 AI 服务或模型；已有 profile 可以复用 |

例如同一个 personal 机器人同时处理灵感和项目记录：保留一个 apps，使用两个 pipelines，
新业务群通过 routes 指向项目记录。未匹配路由的消息继续进入 apps.default_pipeline。
一条消息只选择一个流程；同一群不会因新增流程就自动写入多份文档。
当前匹配条件是应用、chat_id、chat_type，加可选发送者／@ 过滤；尚不支持按正文关键词或命令选择不同业务。

只把另一个群接入已有灵感流程，增加一条指向 inspiration 的路由即可。
如果默认流程本来就是 inspiration，新群不需要专门配置路由也会进入它。

## 2. 新增业务的完整步骤

下面以新群的项目记录为例，不包含真实应用凭证或会话 ID。
先用 [操作手册的来源清单步骤](操作手册.md#4-来源清单如何获取正确-id) 取得新群 chat_id。

### 第一步：准备提示词

在配置根目录创建 `config/prompts/project-notes.md`，例如：

```markdown
请按原始时间整理以下项目记录。
分别列出进展、待办、问题和后续想法；保留原文中的日期和事实。
不要替用户执行事项，不要编造负责人或截止日期。
```

先创建非空提示词文件，再修改 TOML。配置会检查所有引用的提示词，缺失会拒绝整份更新。
Docker 中在宿主机挂载的 config 目录创建，容器中的相对路径仍写 `config/prompts/project-notes.md`。

### 第二步：一起添加路由和流程

在 `config/feishu.toml` 末尾追加完整配置，替换示例 chat_id：

```toml
[[routes]]
id = "project-group"
app = "personal"
chat_id = "oc_replace_with_project_group_id"
pipeline = "project_notes"
require_at = false
allowed_sender_ids = []

[[pipelines]]
id = "project_notes"
handler = "markdown_collect"
input_path = "data/project-notes/pending.md"

[pipelines.ai]
enabled = true
profile = "daily"
prompt_path = "config/prompts/project-notes.md"
daily_time = "01:00"
timezone = "Asia/Shanghai"

[pipelines.output]
path = "data/my-results/{pipeline_id}/{date}-{run_id}.md"

[pipelines.delivery]
app = "personal"
receive_id_type = "chat_id"
receive_id = "oc_replace_with_result_group_id"
```

daily 必须是已经存在并配好的 AI profile；项目记录可以复用它，也可以新增不同的 profile。
只有原文采集需求时可以省略 ai、output、delivery；只保存 AI 结果时省略 delivery。
同群回传时两个 chat_id 填同一个群 ID；给个人发送则 delivery 用 open_id 和该应用下的发送者 open_id。
不同流程使用不同输入路径；模板变量与输出历史规则见操作手册。

将路由和它引用的流程一起保存，避免短暂出现引用不存在的状态。
不要重复使用已有 route／pipeline ID；也不要为同一应用和同一会话重复配置冲突路由。
如果将原灵感群改为项目记录，该群后续消息进入新流程，未匹配的其他来源保持默认流程。
已经接收的记录、原文文件及已创建任务不会自动搬迁或重新分流。

### 第三步：确认热更新已生效

本地从仓库根目录执行：

```bash
uv run python -m app.feishu_cli validate
uv run python -m app.feishu_cli logs --role collector --lines 50
uv run python -m app.feishu_cli logs --role processor --lines 50
```

validate 只验证磁盘上的新配置，不代表运行进程已经采用它。
两个正在运行的角色会在下一事件或后台轮询检查变化，默认约一秒；
日志中的 `event=config.loaded version=...` 表示已接受新版本。
`event=config.rejected` 表示仍使用旧版本，需修正引用、路径、提示词或需要重启的参数。
没有启动的角色会在下次启动时读入最新配置。

然后在新业务群发送一条测试文本，确认 `data/project-notes/pending.md` 出现该条记录：

```bash
uv run python -m app.feishu_cli sources --app personal --kind group
uv run python -m app.feishu_cli status
uv run python -m app.feishu_cli process project_notes
```

process 默认只预览，不请求 AI。确认后可加 --execute 手动处理，它会请求真实 AI，
并在配置 delivery 时发送到真实目的地。实例有多个时从 status 选择 --stream-id。
新增流程／新批次通常从下一次凌晨 01:00 开始调度，不会因为配置热更新就立即提交 AI。

Docker 中用现有容器查询，无需另启动长连接：

```bash
docker compose exec feishu-inspiration python -m app.feishu_cli validate
docker compose exec feishu-inspiration python -m app.feishu_cli logs --role collector --lines 50
docker compose exec inspiration-processing python -m app.feishu_cli logs --role processor --lines 50
docker compose exec inspiration-processing python -m app.feishu_cli process project_notes
```

外部 PostgreSQL 部署为命令添加 `-f docker-compose.external-postgres.yml`。

## 3. 哪些变化需要重启

| 变化 | 是否需要手动重启 | 生效范围 |
|---|---|---|
| 增加／修改 routes | 否 | 新收到的消息按新规则匹配 |
| 新增使用 markdown_collect 的 pipeline | 否 | 新消息建立该流程实例，整理角色按新配置调度 |
| 修改提示词、已引用 profile 的模型／Base URL／参数、输出位置或投递对象 | 否 | 新任务采用新值；已有任务保留创建时的非敏感配置 |
| 新增 AI profile，密钥变量已存在于运行进程环境 | 否 | 新流程／新任务可引用它 |
| 新增／禁用／移除 apps，凭证变量已存在于运行进程环境 | 否 | 采集角色自动创建／关闭对应连接，其他应用继续工作 |
| 修改 apps 的凭证变量引用或飞书 API 域名 | 否，前提是新凭证变量已存在 | 自动重建对应应用连接，连接重建可能短暂中断该应用采集 |
| 在 .env 添加新机器人／AI 密钥或修改变量实际值 | 是 | 重启使用这些变量的采集／整理角色；.env 不热读取 |
| 修改 runtime 任意字段或 observability.log_dir | 是 | 重启读取同一 TOML 的采集与整理角色；在线修改整份配置会被拒绝 |
| 开发新的处理器、修改 Python 代码或生产依赖 | 是 | 本地重启受影响角色；Docker 发布新镜像并更新受影响容器 |
| 新业务增加状态表或字段 | 按该业务迁移方案 | 先备份／迁移，再运行新代码；普通 routes／pipelines 扩展不新增表 |

当前注册的处理器为 markdown_collect：适用于文本采集到 Markdown 和可选 AI 整理。
其他动作，例如调用新的业务 API 或识别新的消息类型，需要实现、注册和测试对应处理器，不能只改 handler 名称。
飞书 worker 是独立进程，Uvicorn --reload 不会替它重载 Python 代码。

新增机器人常需要在 .env 放入新的变量，因此实际操作通常要重启一次相关角色；
只有变量已随进程启动载入时，单纯增加 apps 才能直接热生效。先准备凭证，再启用 apps。

## 4. 需要重启时怎么操作

本地：用 Ctrl+C 停止受影响的 collect／worker 终端，再运行原命令。
采集与整理都要使用同一份 TOML 与状态库；export 只作用于当前终端，统一放 .env 更便于多终端使用。
不要同时留下两份相同角色进程，否则会触发角色锁冲突；不同机器也不能重复连接同一应用。

```bash
# 采集终端
uv run python -m app.feishu_cli collect
```

```bash
# 整理终端
uv run python -m app.feishu_cli worker
```

Docker：仅改 TOML／提示词时，编辑宿主机挂载文件，随后按第三步验证即可。
仅改 .env 时，Compose 的 env_file 需要重新创建容器，普通 docker compose restart 不会更新容器环境：

```bash
docker compose --profile inspiration --profile inspiration-ai up -d --no-deps --force-recreate feishu-inspiration inspiration-processing
```

该命令重建这两个飞书角色的容器，会短暂中断采集／整理；数据保留在持久化挂载和状态库中。
如果只影响一个角色，可以只指定对应服务。runtime 或日志目录修改也可用该命令重建相关角色。
修改代码需要先通过发布流程产生新镜像，更新镜像版本并 pull，再重新创建受影响容器。
涉及新迁移时先按部署手册备份并完成迁移，不能直接用 --no-deps 跳过迁移准备。
生产部署机继续只拉取发布镜像，不构建源码。
