## 1. 目标与现状

用户只需要两项能力：随时通过飞书记录内容；每天指定时间，按指定提示词交给 AI 整理。
记录可以是想法、任务、语录或其他文本，采集时保留原文，不预先分类。
用户人工删除待处理文档，作为停止后续 AI 提交的方式；新消息到来后重新创建文档。

用户已确认：AI 使用兼容 OpenAI 的服务，Base URL 和模型可自定义；处理结果保存到参数指定的
Markdown 路径，并向配置的飞书群聊或私聊发送一份。
2026-10-02 补充决定：北京时间每天凌晨 01:00 执行；默认接收应用收到的私聊和群聊消息，
不要求 @、不限制发送者，保留可选过滤配置；来源 ID 通过来源清单与限时发现日志提供。
每个处理流程只有一份待处理文档，可重跑；快照用于固定某次处理的输入。
AI 客户端抽象为全项目可复用能力，Base URL、模型、提示词及文件路径均通过配置指定。
飞书权限已由用户处理，本次无需再次确认或申请。
进一步调整：日常不逐条打印完整来源信息，提供可查询来源清单和自动到期的发现模式；
日志必须同时限制保留时间与容量，避免持续积累。

本轮核对的代码：

- `daily-claw/src/feishu_bot/main.py`：单应用长连接、文本追加、表情回执，无定时器和 AI 调用。
- `app/services/inspiration.py`：上述能力已经整合，增加后台线程、HTTP 超时和进程内最近
  2,000 条消息去重；仍只有一个文件，未按应用、会话或发送者分流。
- 当前时间格式只有 `HH:MM:SS`，跨日积累时不能区分日期。
- 当前内存队列和去重状态不能跨重启恢复；文件写入失败后没有持久化重试。
- `app/workers/feishu_inspiration.py` 是独立进程；两份部署 Compose 都通过 `inspiration`
  profile 挂载数据目录并启动采集，不在 FastAPI 生命周期中建立长连接。
- 当前存在独立的 Notion 投递任务、租约和重试实现，可以参考其机制，但不混用其业务表。
- 当前 `setup_logging()` 使用控制台 `basicConfig`，两份部署 Compose 均未显式指定日志轮转；
  宿主机实际默认日志驱动未在本轮检查，不能据此断言线上已有轮转或没有轮转。

当前仓库没有 `docs/SETP.md`。本方案按现有开发规范的“现状、设计、实施、验证、交付”组织。

## 2. 用户流程与文件规则

```text
用户向机器人私聊，或在机器人所在群聊发消息
  → 更新来源清单，按需输出限时发现日志
  → 按配置匹配路由，未显式匹配的私聊／群聊进入应用默认流程
  → 记录完整北京时间与原文到对应待处理文档
  → 写入成功后，添加飞书 OK 回执

每天北京时间凌晨 01:00（可配置）
  → 检查待处理文档
  → 不存在／空白：跳过，不请求 AI
  → 存在且非空：读取快照，按该流程提示词请求 AI
  → 结果保存到参数指定的独立 Markdown 路径
  → 向配置的飞书群聊或私聊发送整理结果，分别记录保存与发送状态

用户阅读结果后，人工删除待处理文档
  → 后续没有文档时不提交
  → 新消息到来时创建新的待处理文档，开始新一轮积累
```

文件规则：

1. 每个流程只有一份可编辑／删除的待处理文档，是累计收集箱，不强制每天拆文件。
   路径可完全自定义，也可以使用应用 ID／来源会话 ID 模板，不固定为 `notes.md` 或 `inbox.md`。
   如果不同来源要合并进这一份文档，应映射到同一个流程；如果按来源分文件，则每个来源形成
   独立的流程实例，各自只有一份待处理文档。
2. 记录使用消息原始发送时间，格式包含日期，例如 `2026-10-01 14:30:00 +08:00`；
   多行文本保留结构。群聊场景同时保留发送者和来源，内部保留消息 ID 用于去重。
3. 定时处理的是触发时文档中的全部内容，可能跨越多天；结果注明处理时间与覆盖范围，
   不把旧内容误标成当天记录。
4. 文件存在且非空，即使内容没有变化，次日也可以再次整理；支持手动重跑。
   同一次定时触发的重试与次日新触发必须区分，不能用内容哈希永久阻止次日处理。
5. AI 成功后不自动删除、不覆盖待处理文档。结果写到独立目录，例如
   `data/feishu/inspiration/results/<处理时间>-<任务ID>.md`，避免同日多次处理互相覆盖。
   输出支持配置目录与文件名模板；如果指定固定文件路径，默认另存历史版本再原子更新该文件。
6. AI 失败保留原文，记录错误并有限重试；结果保存失败不能标记整个任务成功。
7. AI 请求期间的新消息继续追加到收集箱；本次只处理已读取的快照，新内容进入下次处理。
8. 删除文档意味着关闭这一批输入。扫描和恢复任务不得从历史数据重新生成已删除的文档；
   新消息创建的新文档必须使用新批次标识，旧任务不能修改新批次。
9. 尚未发送的 AI 任务在执行／重试前核对文件和批次：文件已删除或批次已更换则取消。
   请求已经发出后无法撤回，本次结果可正常保存，但不能恢复收集箱。
10. 快照只为已创建任务的执行与恢复服务，不作为永久原文副本；成功／取消后的清理策略
    需明确。删除收集箱不等于删除已生成结果或 AI 服务已接收到的内容。
11. 同一流程同一时刻最多执行一个 AI 整理任务。失败任务可以重试；下一次定时／手动运行
    不叠加执行或积压多份“待处理文档”，具体领取状态可通过日志查看。
    快照是内部任务输入，结果是处理产物，两者均不参与“当前待处理文档”的计数。

## 3. 标准化接入：应用、路由、流程

| 对象 | 管理什么 | 示例 |
|---|---|---|
| 飞书应用 | App ID、密钥引用、默认流程、长连接、token、消息／表情 API | 个人机器人、工作机器人 |
| 路由 | 哪个应用、会话、发送者的消息送到哪个流程 | 灵感群 → inspiration |
| 处理流程 | 收集文件、处理器、提示词、AI 配置引用、执行时间、结果位置 | 灵感整理、项目记录 |

同一个应用可以服务多个群。多个来源也可以显式映射到同一个流程，共享一份收集箱。
以后增加群聊或复用现有整理方式，只增加配置；增加新的业务动作时，增加一个处理器并注册，
复用接收、路由、去重、持久化和运行状态机制。

第一版采用受校验的 TOML 配置与独立 Markdown 提示词文件，密钥通过环境变量引用；
使用 Python 3.11 内置 TOML 解析能力，避免为配置额外引入框架。
配置提供版本号、稳定应用别名、稳定流程 ID 和启用开关。

下面是结构示意，字段尚未实现，不可直接作为当前运行配置：

```toml
version = 1

[observability]
level = "INFO"
summary_interval_seconds = 300
log_dir = "data/logs/feishu"
retention_days = 7
max_file_mb = 10
max_total_mb = 100 # 每个运行角色的文件日志预算
console = false # 生产正式日志写文件；控制台镜像可选启用

[observability.discovery]
enabled = false
duration_seconds = 600 # 启用后自动到期，不因收到消息续期

[[apps]]
id = "personal"
app_id_env = "FEISHU_PERSONAL_APP_ID"
app_secret_env = "FEISHU_PERSONAL_APP_SECRET"
default_pipeline = "inspiration" # 私聊／群聊均可进入默认流程

[ai_profiles.daily]
provider = "openai_compatible"
base_url = "https://example.invalid/v1"
model = "selected-model"
api_key_env = "COLLECTION_AI_API_KEY"
timeout_seconds = 120

[[routes]]
id = "inspiration-group"
app = "personal"
chat_id = "oc_example"
allowed_sender_ids = [] # 空列表表示不限制发送者，可选填 open_id
require_at = false
pipeline = "inspiration"

[[pipelines]]
id = "inspiration"
handler = "markdown_collect"
input_path = "data/my-inspiration/pending.md" # 用户自定义

[pipelines.ai]
enabled = false
profile = "daily"
prompt_path = "config/prompts/inspiration.md" # 不同流程可用不同提示词
daily_time = "01:00"
timezone = "Asia/Shanghai"

[pipelines.output]
path = "data/my-results/{pipeline_id}/{date}-{run_id}.md" # 用户自定义

[pipelines.delivery]
app = "personal"
receive_id_type = "chat_id" # 私聊可使用 open_id
receive_id = "oc_result_example"
```

选择按来源分文件时，`input_path` 可写成
`data/feishu/{app_id}/{chat_id}/pending.md`；相应结果与任务状态也按该来源流程实例隔离。
如果希望所有群和私聊合并成一个收集箱，则使用示例中的固定自定义路径。
模板支持的变量及实例键必须固定并校验，不把不同来源实例误合并为同一个运行锁。

路由约束：

- 用稳定的 `app_id/chat_id/sender_id` 识别来源，显示名称不作为匹配主键。
- 私聊／群聊均默认接收，不要求 @、不限制 User ID。`require_at` 和
  `allowed_sender_ids` 是可选过滤条件，不配置时不进行相应过滤。
- 先匹配显式会话路由，再使用应用默认流程；显式路由的过滤条件不满足时不回落默认流程，
  避免绕过用户主动设置的过滤。相同优先级的重叠规则在配置加载时拒绝。
- 每个事件默认只送往一个流程，来源清单与限时发现模式在路由过滤前观察元数据。
- 不采集本系统发送的结果消息，防止回复形成循环；这与是否要求用户 @ 无关。
- 接收全部消息是指消息来源；第一版内容处理仍支持文本。非文本事件计入跳过统计，
  开启限时发现／调试时可查看其类型与来源，不把忽略误报为采集成功。
- 路径根目录可配置，并校验模板变量及输入／输出冲突，不把固定文件名或仓库内路径作为要求。
  容器路径通过数据卷映射；按来源命名时只采用受校验的 ID，不直接使用群名称拼接路径。
  配置文件和提示词可以版本管理，运行数据保持忽略。

### TOML 与提示词热加载

采用“启动加载 + 使用前检查 + 调度周期检查”，不使用文件监听器，不在每条消息上重复解析全文：

1. 启动时解析并校验 TOML 与其引用，生成不可变配置版本；无有效初始配置时明确报错。
2. 每次消息处理入口检查文件变更标识；调度／连接管理每秒检查一次，以便无消息时也能更新。
   标识使用修改时间、大小等元数据；发生变化才重新读取、解析和校验。内容指纹识别版本。
3. 完整校验后原子替换当前版本。文件暂时不存在、半写入、语法错误或引用无效时继续使用
   最近有效版本，记录错误；按变化标识限制重复报错，不刷屏。
4. 提示词文件也检测变化：新创建的任务使用最新有效内容；已创建任务固定输入、提示词、
   Base URL／模型及输出目标，重试不因后来修改配置而变成另一项任务。密钥仅保存引用。
5. 配置修改影响下一条消息／下一项新任务，不迁移已有文档、不改变已领取任务。
   修改输入路径时明确日志提示旧文件仍保留，后续写入新路径；不会悄悄搬动原文。
6. 修改执行时间后重算未来触发点，不因热更新立即补跑过去时刻；显式手动重跑另行处理。
   禁用流程／AI 时停止创建新任务，并取消尚未执行的生成任务，已发出请求无法撤回。
7. 应用连接参数不同于路由参数。新增／删除应用、修改 App ID 或密钥引用时，由连接管理器
   重新启动相应连接进程，其他应用连接保持运行；这是定向重连，不宣称连接无中断热切换。
   未改 TOML、只修改容器外 `.env` 的内容不会改变现有进程环境，应按部署方式重建相关容器。
8. 提供显式配置重载命令用于诊断／立即检查；自动加载不依赖用户执行该命令。
   Docker 挂载整个配置目录，避免单文件挂载在编辑器原子替换文件后仍指向旧文件。

可热更新项：路由、默认流程、User ID／@ 条件、文件路径、AI 配置、提示词、调度时间、回复目标。
日志记录加载成功的配置版本及受影响对象，凭证值不进入日志。

### 来源清单、限时发现与运行日志

将“配置需要的来源元数据”与“运行诊断日志”分开，日常不逐条打印机器人的完整信息。

**来源清单：**利用已有 PostgreSQL 保存观察到的应用、会话、发送者 ID 及首次／最近出现时间，
按身份去重更新；不保存消息正文，不额外拉取群／用户资料。
提供只读 CLI 列出来源并支持按应用、群聊／私聊筛选与分页，输出可直接填入 TOML 的 ID。
无需依赖历史日志才能找到配置值。首次看到新的会话只输出一条简短发现提示；重启后不重复提示。
来源清单仅表示系统实际收到过的来源，不宣称列出机器人有权限访问的所有群／用户。
未配置来源的元数据设置独立保留期限和数量上限，避免来源清单自身无限积累。

**发现模式：**需要确认某条消息的 User ID、@ 状态或路由时，显式开启，例如 10 分钟。
启用期间以 INFO 输出来源元数据、匹配规则与写入路径，到期自动关闭；可提前关闭。
支持 TOML 启用或管理命令启用；管理命令通过已有进程共享状态生效，不建立第二条飞书连接。
到期时间固定，不因新消息、无关配置热加载或 worker 重启而自动延长。
发现状态保存绝对到期时间，并限制最大持续时长及输出速率；超限只记录省略计数。

发现模式示例：

```text
event=feishu.discovery status=enabled app=personal expires_at=2026-10-02T10:10:00+08:00
event=feishu.source app=personal chat_type=group chat_id=oc_example sender_open_id=ou_example message_id=om_example has_mentions=false mentioned_bot=false pipeline=inspiration route=default path=<实际文件路径>
event=feishu.discovery status=expired app=personal
```

**普通运行日志：**

- 应用启动／重连、配置加载／失败、任务开始／结果、最终失败记录 INFO 或更高等级。
  App ID 在连接生命周期日志记录，后续只用稳定应用别名标识，不每条重复打印。
- 每条成功采集、重复、过滤等细节默认放 DEBUG；INFO 按 5 分钟汇总接收、写入、
  重复、过滤、不支持类型与失败数量，没有活动则不打印空汇总。
- 没有待处理文档的定时检查只记录该次每日触发的跳过结果，不每秒轮询打印。
- 新错误立即输出；同一重复错误按时间窗口限频，随后汇总重复次数，避免异常风暴。
  保留错误分类、应用／流程及消息 ID 或任务 ID，足以定位失败。
- `sender_open_id` 是默认路由 User ID 类型；其他用户 ID 仅在事件确有提供时输出，
  明确区分类型，不将缺失字段伪造为可用 ID。
- 有 @ 时输出目标 ID／类型以及是否 @ 本应用机器人；暂不可确认时标记 `unknown`，
  不以 `has_mentions=true` 代替“@ 了本机器人”。
- 日志不打印消息正文、提示词正文、完整请求载荷、密钥或 token。

### 日志保留与容量上限

建议第一版使用下面的默认值，均通过配置修改：

| 日志层 | 策略 | 保证与边界 |
|---|---|---|
| 应用文件日志 | 每日切分；单文件 10 MB 再切分；保留最近 7 天；每运行角色总量 100 MB | 时间与容量任一超限均清理较旧关闭文件，可能不足 7 天 |
| 生产容器 stdout/stderr | 本模块容器使用 none 驱动，正式日志由受控文件保存 | 无 Docker 持久化副本，docker logs 不提供日志 |
| 可选控制台镜像 | 开启时 Compose 使用 Docker local；10 MB × 5 个文件 | 约 50 MB 的轮转预算，有容量限制，无按 7 天删除保证 |

- 应用文件日志是需要按天保留的正式日志。清理在启动与定时维护中执行，运行时至少每小时检查，
  不依赖新日志产生才清理；因此时间边界是 7 天加最多一个维护周期。
- 容量检查随写入／轮转执行，不等每小时清理；单条日志也限制长度。
- 多应用连接进程通过采集角色的单一日志写入端汇总，整理 worker 独立写入；
  不允许多个进程直接轮转同一个文件。总量预算覆盖对应角色目录内的全部日志段。
- 文件清理只处理本模块明确拥有的日志文件，不触碰输入、快照、结果、数据库或 Docker 内部文件。
- 默认生产模式关闭控制台镜像，正式日志只保存在按时间／容量清理的文件中，通过
  文件／日志查询命令查看。错误同样写正式日志，文件写入端初始化失败时进程明确失败，
  不悄悄退化为无日志运行。仅对本模块采集／整理容器应用此策略，不调整其他服务。
- Docker local 的选项是容量／数量限制，不能把 `max-file=7` 描述成“保留 7 天”。
  若显式选择控制台镜像模式，缓存可能保留超过 7 天，应明确其边界，不能宣称所有副本都已过期。
- Docker 的日志驱动与轮转选项需要在部署时重建相关容器才会应用；本轮不改宿主机全局配置，
  不重启服务，不清空现有 Docker 日志。参考
  [Docker 官方 local 日志驱动说明](https://docs.docker.com/engine/logging/drivers/local/)及
  [日志驱动配置说明](https://docs.docker.com/engine/logging/configure/)。
- 操作手册提供来源清单、发现模式及正式文件日志的查看命令；控制台镜像启用时也可使用
  `docker compose logs --tail=100 -f feishu-inspiration`，外置数据库部署加相应 `-f` 文件参数。

### 已确认的 AI 与输出参数

AI 客户端以兼容 OpenAI 的 Chat Completions 请求为第一版接口约定，发送指定提示词与文档输入，
获取文本结果。接口语义参考 [OpenAI 官方 Chat Completions 文档](https://developers.openai.com/api/reference/chat-completions/overview)。
第三方服务是否完整兼容，仍需在指定服务的受控验收中核对。

- `ai_profiles.<名称>.base_url`：用户指定的 API 前缀，例如 `https://example.invalid/v1`；
  明确拼接 `/chat/completions`，防止重复添加 `/v1`。
- `model`、`api_key_env`、超时与输入／输出预算：独立配置，不绑定某一家服务或模型；
  可定义多个具名 AI 配置供不同流程共用／选择。
- `prompt_path`：用户指定的提示词文件，与采集路由分别配置。
- `output_path`：用户指定的 Markdown 文件路径或模板，与输入文件必须不同。
  Docker 场景下，路径应对应挂载的持久化目录；宿主机路径与容器路径在操作手册中明确映射。
- `delivery.app`、`delivery.receive_id_type`、`delivery.receive_id`：指定使用哪个机器人，
  向哪个群 `chat_id` 或用户 `open_id` 发送；可与采集来源不同。
- 飞书发送整理正文；长内容按平台限制拆分或转为文件消息，不静默截断或仅发送完成通知。
  文档存储成功后才开始发送，保存和发送分别记录状态，发送失败只重试发送，不重新调用 AI。

配置中的路径与接收方均为占位示例，用户将在运行参数中指定实际值。

飞书应用接收／发送权限已由用户处理，按可收到私聊和群聊消息设计，不把权限申请作为前置待办。
继续沿用企业自建应用机器人和长连接；运行时权限错误作为明确失败日志，不悄悄跳过。
参考：[飞书官方接入方案中的消息权限说明](https://open.feishu.cn/solutions/detail/ticket?lang=zh-CN)、
[接收消息事件](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/events/receive)。

## 4. 代码与运行边界

建议分层：

```text
飞书适配器：连接、事件转标准消息、token、回执
  → 路由器：来源匹配到流程
  → 处理器：第一版实现 markdown_collect
  → 文件存储：串行写入、批次识别、快照、结果原子保存

定时调度：按流程生成持久化任务
  → 业务整理服务：组织输入、加载提示词、调用通用 AI 客户端
  → 通用 AI 客户端：按配置执行兼容 OpenAI 请求、验证响应
  → 结果存储：独立 Markdown、任务状态
```

- `app/workers/` 只组装生命周期；通用接入与业务逻辑在 `app/services/` 中分离。
- 继续使用一个采集运行角色。多个群不增加进程或容器；多个应用每个应用需要自己的连接，
  建议由同一采集服务管理独立连接进程，具体启动方式在实现时验证当前 SDK 的事件循环约束。
- 每日调度与 AI 消费建议放在一个独立整理 worker，复用后端镜像和数据挂载；
  多个流程共用此 worker，不为每个流程建立容器。
- 长连接与 AI 任务均不加入 FastAPI lifespan。慢 AI 调用不能阻塞消息采集。
- 新建全项目共用的兼容 OpenAI AI 客户端与配置，支持用户自定义 Base URL 和模型；不恢复废弃的
  `app/utils/ai_client.py`，不把旧视频 AI 配置当作新业务配置。
- 第一版提示词独立存放，可修改；任务保存所用提示词和模型版本标识，便于解释结果。
  默认输出可包含想法、待办、语录和其他记录，保留来源时间，不编造事实或自动执行待办。

### 通用 AI 模块职责

建议使用 `app/services/ai/` 放置新的通用客户端、配置／请求／结果类型及调用错误。
它不依赖灵感模型、飞书 SDK、具体文件名或定时器，后续业务可以直接调用：

```text
业务选择具名 AI 配置 + 指定提示词／messages
  → 通用客户端
  → 文本结果、服务请求 ID、用量（若服务提供）、结束状态
  → 调用方自行保存、发送或继续处理
```

- 统一处理 Base URL 拼接、鉴权引用、超时、响应校验、HTTP／服务错误与可重试性分类。
- 模型名称原样传递；提示词默认在业务／任务层加载，通过 messages 传入，客户端不预设总结格式。
- 调用参数提供受校验的可选扩展配置，便于不同服务／模型使用不同生成参数；
  核心 `model/messages` 与鉴权字段不能被扩展参数意外覆盖。
- 网络重试只由一个明确层负责：通用客户端返回错误分类，持久化任务层决定次数／退避，
  避免客户端自动重试与 worker 重试叠加计费。
- 不保存敏感业务内容到日志，不自行读写收集文件、创建任务或发送飞书消息。
- 通用模块采用明确的请求／结果契约，使用本地 HTTP 替身验证；不同业务不用复制一份客户端。

## 5. 持久化、重试与调度

利用已有 PostgreSQL 保存接收去重状态和 AI 运行任务，新增独立模型及 Alembic 迁移。
不引入 Redis、消息中间件或完整工作流引擎。

- 接收去重键使用应用身份与 `message_id`；同一句文本作为两条不同消息发送仍记录两次。
- 接收先形成可恢复的持久化记录，文件写入成功后再回执；回执失败单独重试，不重复写原文。
- 数据库事务与文件写入不是一个原子操作。实现必须覆盖“文件已写入但状态未提交”的崩溃窗口，
  使用可核对的消息标识与按流程串行写入，不能仅凭数据库唯一键宣称文件恰好写入一次。
- 已落盘的原文不在数据库无限期重复保留；待写入内容、输入快照和元数据区分管理。
  文件删除后的恢复规则必须遵守关闭批次的语义，不能因重试复活旧文件。
- AI 任务按“流程 ID + 计划执行时刻”唯一创建，输入快照／提示词固定；内容哈希用于核对，
  不作为跨日禁用处理的条件。
- 任务区分待执行、执行中、成功、失败、取消，记录尝试次数、下次重试时间、租约和结果路径。
  AI 生成、Markdown 保存和飞书发送的状态分别记录；发送失败不能被整体成功状态掩盖。
- 多 worker 或重启时通过数据库领取锁和租约避免同一任务被并发执行。
- 外部 AI 在响应丢失时可能已经执行并计费；本地幂等不等于服务端恰好执行一次。
  按所选服务能力使用请求幂等键，无法确认的超时按有限重试和清晰状态处理。
- 每日默认 01:00，按 `Asia/Shanghai` 计算，保留流程级时间配置。
  建议停机后当日补执行最多一次；不批量补跑过去多天，
  避免反复提交同一收集箱。此策略与手动重跑入口一并纳入测试。
- 缺失文档／空白文档只产生跳过状态，不调用 AI；文件读取失败是错误，不能当作没有内容。
- 超出模型输入预算时明确失败并保留原文；不能静默截断。分段整理可在确定模型和数据量后补充。
- 首版提供配置校验、查看路由／运行状态、指定流程手动处理的命令；手动处理默认不等待定时。
  默认自动化测试与预览命令不发送真实请求，真实手动执行需要显式执行模式。

## 7. 验证与回退计划

关键验收用例：

- 私聊／两个群／两个应用正确路由；显式分流不串文件，其他来源进入应用默认流程。
- 默认无需 @、不限 User ID；主动配置过滤后按条件处理，不通过默认流程绕过过滤。
- 来源清单可筛选／分页，提供实际可用 ID；新来源提示跨重启去重，不存正文。
- 发现模式输出 ID 类型、@ 状态和路由结果，到期后停止；无关配置重载／重启不续期。
- 普通 INFO 不逐条打印成功采集；空轮询不刷日志；重复错误限频并保留计数。
- 日志按天及大小轮转、到期清理、目录总量上限均生效；无新日志时维护仍可清理旧文件。
- 多进程日志采用单写入端；清理只作用于本模块日志，容器缓存与正式文件保留边界明确。
- 无消息时配置依然能在检查周期内生效；改时间不补跑过去时刻；非法配置沿用有效版本。
- AI 配置、路由、提示词热更新影响新任务；已有任务重试保持其非敏感参数与目标。
- 新增／删除应用或修改连接配置仅重启目标连接；运行中环境变量变化的部署边界清楚。
- 自定义固定路径／来源模板均正确解析；同一实例只有一份待处理文档和一个执行中的整理任务。
- 文本、多行、空文本、非法事件、非文本消息、跨日时间均符合约定。
- 飞书重复推送、重启、写入中崩溃、文件写入失败、HTTP 200 但业务 code 非零均正确处理。
- 回执失败后原文不重复；采集队列故障可见，待处理消息有明确恢复边界。
- 缺失文件、空文件不调用 AI；非空文件与指定提示词产生结果。
- 保留文件跨日再处理；同一次触发／多 worker 不重复创建任务。
- AI 期间收到新消息、删除文件、删除后新建文件、取消后的重试均不覆盖／复活输入。
- AI 超时、限流、认证失败、响应为空、结果写入失败保持清晰状态，不丢原文。
- 自定义 Base URL 的路径拼接、模型原样传递、Markdown 指定路径、飞书指定接收方均正确。
- 两种独立业务通过同一个 AI 模块使用不同具名配置和提示词，错误分类与响应契约一致。
- 飞书发送失败只重试发送；长结果完整送达；发出的结果不被机器人重新采集。
- worker 重启后的任务恢复、当日补执行、提示词更新、输入超长符合既定策略。
- 睡眠、运动、Notion 与废弃路由的既有行为通过回归验证。
