# 睡眠与运动数据看板

## 1. 目标与范围

新增一个独立容器运行的响应式前端，以睡眠状态为主，默认展示当前月；运动页通过 `/sport` 直接访问，不在睡眠页提供入口。页面只读取当前 API Key 对应用户的数据。

本需求同时补齐看板所需的本地查询接口。PostgreSQL 仍是本地事实来源；删除只影响本地记录，不会删除已经同步到 Notion 的副本。

## 2. 领域规则

- 数据库继续保存独立的入睡、起床休息事件，不迁移或重写历史数据。
- `rest_type` 的固定契约为 `0=睡眠（入睡）`、`1=起床`；模型常量、创建接口和 Notion 睡眠/起床库选择均使用此约定。采集端可显式提交该值；省略时按“12 小时超时重锚定”规则自动判定，详见[睡眠打卡自动纠偏](../睡眠打卡自动纠偏/README.md)。
- API 按时间顺序把一次入睡和其后 24 小时内最近的起床配成睡眠会话。
- 完整会话的“睡眠日”固定为起床当天：前一晚入睡和当天凌晨入睡，都会归到当天起床完成的睡眠；单侧错误事件仅按现存事件当天展示，且不参与统计。
- 睡眠时长为起床时间减入睡时间，仅完整且时长大于 0、小于 24 小时的会话参与时长统计。只有入睡或只有起床的单侧事件是错误数据：API 返回 `missing_wake` 或 `missing_sleep`，保留在明细供删除/排查，但不计入时长、平均入睡/起床、最长最短、年度统计或热力时长；日历以红色感叹号、明细以红色状态标识。
- 删除一个睡眠会话时，同时删除该会话当前配对的入睡与起床事件；不完整会话只删除存在的事件。界面必须二次确认并明确显示影响范围。
- 运动 `duration` 的业务单位固定为分钟，API 对外使用 `duration_minutes` 明确表达。
- “其他”且时长为 2 分钟（允许浮点存储误差）的运动是红色个人标记；“其他”且时长为 30 分钟是黄色特殊标记。API 分别输出 `is_marker` 与 `is_thirty_minute_marker`，前端用颜色、图例和文字共同提示。

### 运动时长历史修正事项

早期文档曾错误声称运动时长单位为小时。现有 `sport_record.duration` 中已经写入的数据不能据此自动乘以 60：来源快捷指令在不同时期可能已经按分钟提交。上线看板前应先备份并抽样对照 Notion 原始页面与 `notion_ingest_events.original_payload`，确认受影响记录后再做一次明确的数据修正。本需求只修正新契约、统计和展示语义，不自动改写历史数据。

## 3. 页面信息结构

### 睡眠页 `/`

1. 月份、年份、近三年三个展示范围，默认当前月；近三年模式的统计和分页明细仍覆盖全部历史，但热力图最多渲染滚动最近三年；
2. 平均时长、完整会话数、最长时长、平均入睡和起床时间；最长一晚会显示睡眠日；
3. 当前月日历热力图，不同蓝色深浅表示时长区间，并以皇冠、月亮、闹钟分别标识睡得最久、最早入睡、最早起床的睡眠日；
4. 小型醒来城市排行，只统计完整会话中起床事件携带的城市，最多显示前三名；
5. 可翻页会话表格，展示睡眠日、入睡、起床、时长、位置和完整性；
   单侧错误事件也保留在表格，明确显示缺少的是入睡还是起床；
6. 会话删除确认框；
7. API Key 连接界面，默认仅保存在当前浏览器会话，可选在此设备记住。

### 运动页 `/sport`

1. 当前月、年份、近三年三个展示范围；近三年模式的统计和分页明细仍覆盖全部历史，热力图只渲染滚动最近三年；
2. 次数、总时长、活跃天数、运动标记数；
3. 月历和运动记录表格；
4. 运动日历同时显示“2 分钟标记”红点和高对比的“30”黄色标签；同一天同时出现时保留两种标识，表格用对应文字和颜色说明；
5. 睡眠页不展示运动入口，保留直接链接。

移动端把表格行改为卡片，所有交互目标不小于 44px；颜色不是唯一的信息载体。页面支持键盘焦点、减少动态效果和系统深色模式。

## 4. API

- `GET /api/v1/rest-records/sessions`：按 `scope=month|year|all`、`period`、`page`、`page_size` 返回睡眠会话、统计和热力数据。前端把 `all` 呈现为“近三年”：摘要与分页仍是全部历史，`heatmap` 只返回滚动最近三年，避免大量 DOM 节点卡顿。`records[].error_code` 标识单侧/异常会话，`heatmap[].error_count` 标识当天错误数量；分页总数包含错误记录，摘要统计不包含。
- `DELETE /api/v1/rest-records/sessions/{anchor_record_id}`：删除一个本地睡眠会话当前包含的休息事件。
- `GET /api/v1/sport-records/`：按相同范围返回运动列表、统计和每日热力数据；`scope=all` 同样只裁剪热力图，统计和分页保留全部历史。

所有接口使用现有 Bearer API Key。年度旧接口继续保留；其日期语义统一为完整会话的起床日期。

## 5. 本地运行与部署

本地开发不依赖 Docker：先准备可访问的 PostgreSQL，配置根目录 `.env`，再分别启动 API 和
前端开发服务器。

```bash
uv sync --locked
uv run python -m app.db.migration_baseline
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --host 0.0.0.0 --port 8000

# 另开终端
cd frontend
npm ci
npm run dev
```

本地前端会把 `/api/` 代理到 `http://127.0.0.1:8000`。后端单元测试
`./scripts/test.sh unit`、前端 `npm run test` 与 `npm run build` 也都不需要 Docker。

最终部署时，前端静态文件已在 GitHub Actions 构建并封装进 Nginx 镜像；NAS 只拉取镜像，再把
`/api/` 反向代理到 FastAPI `web:8000`。Compose 中 `frontend` 是独立服务，默认端口为 `3000`，
可用 `FRONTEND_PORT` 覆盖。

```bash
docker compose pull web frontend
docker compose up -d --wait web frontend
```

外部 PostgreSQL 部署同样不新增数据库容器，只拉取并运行对应镜像。完整镜像标签和部署步骤见
[`docs/容器化部署与本地运行/README.md`](../容器化部署与本地运行/README.md)。

## 6. 验证边界

- 纯函数和 API 单元测试不连接真实数据库、Notion 或 Bark；
- 前端执行类型检查、单元测试和生产构建；
- Docker 可用时再执行真实 PostgreSQL 功能测试和容器健康检查；
- 视觉验收至少覆盖 375px 手机和 1440px 桌面，以及浅色、深色和减少动态效果。
