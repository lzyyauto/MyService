# 纯飞书采集操作手册

当前能力：长连接接收文本 → 保存指定 Markdown → OK 表情回执。总结及 agent 独立处理，暂未接入。
支持 Linux／macOS，Python 3.11。无需 AI 密钥、提示词或 PostgreSQL 初始化。

## 1. 本地运行

```bash
cd /Users/zingliu/Code/my-service
uv sync --locked
# 首次使用才复制；不要覆盖已有私有配置
test -f config/feishu.toml || cp config/feishu.example.toml config/feishu.toml
uv run python -m app.feishu_cli validate
uv run python -m app.feishu_cli collect
```

根目录 .env 最少提供：

```dotenv
FEISHU_CONFIG_PATH=config/feishu.toml
FEISHU_APP_ID=实际应用ID
FEISHU_APP_SECRET=实际应用密钥
```

TOML 的 app_id_env／app_secret_env 填以上变量名，不填实际值。CLI 自动读取配置根目录的 .env，
进程环境优先；不要 source .env。FEISHU_CONFIG_PATH 也可通过 --config 显式指定。
collect 正常启动后常驻运行，默认写正式文件日志。Ctrl+C 停止。

内部 SQLite 自动初始化，无需先执行 init-local；该命令只作为兼容入口保留。
默认路径由 runtime.state_path 控制。已有 FEISHU_STATE_DATABASE_URL 为 SQLite 时继续使用原文件，
所以此前的来源和去重记录不会丢失。该变量为空时不再连接 POSTGRES_*。
如果旧配置显式指定 PostgreSQL 状态 URL，先保留旧库备份，再移除覆盖或指定本地 SQLite；不会自动迁移旧库内容。

本次代码简化完成后：停止原 collect 并按上面命令重启一次；旧 worker 不再使用。
本轮检查到的旧本地 AI 整理进程已停止并确认退出，其他机器上的旧整理进程也应停用。
不要同时对同一应用运行两份采集；同目录角色锁只保护当前共享目录，不能保护不同机器。

## 2. 最小配置与扩展

config/feishu.example.toml 是完整模板。最小主体如下：

```toml
version = 1

[runtime]
root_dir = ".."
state_path = "data/feishu/state.sqlite3"

[[apps]]
id = "personal"
app_id_env = "FEISHU_APP_ID"
app_secret_env = "FEISHU_APP_SECRET"
default_pipeline = "inspiration"

[[pipelines]]
id = "inspiration"
input_path = "data/my-inspiration/pending.md"
```

root_dir 相对 TOML 所在目录，其余相对路径基于 root_dir，也可以指定绝对 Markdown 路径。
新群使用不同文档时，在末尾一起新增：

```toml
[[routes]]
id = "project-group"
app = "personal"
chat_id = "oc_replace_with_real_group_id"
pipeline = "project_notes"
require_at = false
allowed_sender_ids = []

[[pipelines]]
id = "project_notes"
input_path = "data/project-notes/messages.md"
```

pipelines 在这里仅代表文档目标，不代表 AI 流程。复用相同目标只加 routes；
新建不同机器人则加 apps，使用独立密钥变量。默认群聊和私聊都接收，不要求 @，不限制用户。
若只允许自己，将 allowed_sender_ids 设为查询到的 sender_open_id 列表。
未匹配来源进入 apps.default_pipeline；命中路由但被过滤则不回落。
当前不支持正文命令／关键词分流，一条消息只写一个目标。

若按来源分文件，可使用：

```toml
input_path = "data/feishu/{app_id}/{chat_id}/messages.md"
```

不同目标不能共享同一个实际文件。路由／文档路径／开关修改会热读取，默认约一秒。
validate 校验通过后，查 collector 日志的 event=config.loaded；event=config.rejected 表示仍使用旧版。
验证磁盘配置成功不代表旧 Python 进程已经更新程序代码。
既有消息不会重新分流，旧文档也不会自动移动；路径修改只影响后续接收消息。

| 修改 | 是否需要重启 |
|---|---|
| routes、pipelines 文档路径／启停 | 不需要；热加载 |
| apps 新增／删除，凭证变量已在进程环境中 | 自动创建／关闭对应连接 |
| .env 或变量实际值 | 重启采集；不热读取 |
| runtime、日志目录、Python 代码 | 重启采集 |
| Docker env_file | 重新创建采集容器，普通 restart 不更新环境 |

## 3. 获取群聊与个人 ID

先启动采集，在目标群／私聊发一条文本，再查询：

```bash
uv run python -m app.feishu_cli sources --app personal --kind group
uv run python -m app.feishu_cli sources --app personal --kind p2p
uv run python -m app.feishu_cli sources --app personal --limit 100 --offset 100
```

| 字段 | 用途 |
|---|---|
| app | TOML 的机器人别名，配置 routes.app |
| app_id | 核对真实机器人应用 ID；不是 routes.app |
| chat_id | 群／私聊会话 ID，配置 routes.chat_id |
| chat_type | group 群聊／p2p 私聊，可配置 routes.chat_type |
| sender_open_id／sender_id | 同一个应用下的发送者 open_id，配置 allowed_sender_ids |
| user_id | 来源参考，可能为空；不要代替 open_id 过滤 |
| first_seen／last_seen | Unix 秒时间戳，用于对应测试时间 |
| message_count | 观察到的事件数，包含重放可能，非文档去重条数 |

清单仅包括机器人实际收到过的来源。同群不同发送者各一行，重复 chat_id 是正常的。
open_id 与应用相关，不能直接跨机器人复用。新会话首次发现有一条 INFO，不逐条打印机器人资料。

需要详细元数据时临时开启发现：

```bash
uv run python -m app.feishu_cli discover --app personal --seconds 600
uv run python -m app.feishu_cli logs --role collector --lines 100
uv run python -m app.feishu_cli discover --app personal --seconds 0
```

自动到期，最长 3600 秒，重启不续期；每个连接最多每分钟 60 条发现日志。
记录 ID、类型、路由和 mentions，不记录正文和密钥。仅 require_at 时查询机器人身份，查询失败严格过滤。
来源默认保留 90 天、最多 10000 条；其他消息的去重 ID 不受来源目录清理影响。

## 4. 状态、日志与隔离演示

```bash
uv run python -m app.feishu_cli status
uv run python -m app.feishu_cli logs --role collector --lines 100
uv run python scripts/feishu_local_demo.py
```

status 显示目标文件、待写入／失败消息数及待发送／失败回执数，不显示正文。
演示使用临时目录、SQLite 和本机回执替身，故意让第一次回执返回 503，最终 ok:true 表示恢复验证通过。
不会访问真实飞书或 AI，也不会读取／修改用户原文。包含重启去重和删除后新消息重建。
手工模拟消息时使用独立配置与目标目录，避免向自己的正式文档插入测试内容：

```bash
uv run python -m app.feishu_cli --config /你的隔离配置/test.toml simulate --app personal --text '测试文本'
```

日志默认 INFO；逐条成功元数据为 DEBUG；有活动才每五分钟汇总，同类错误限频。
正式日志最多约 7 天、每文件 10 MB、每角色 100 MB；容量满可更早淘汰，启动、写入及每小时维护。
可在 observability 中调整；不清理原文、结果或用户备份。

若写入失败，不给成功回执，状态保留便于排查；回执失败独立重试，不重复追加原文。
默认重试间隔 30 秒、最多 3 次。达到上限后 status 会显示失败，先排查权限／磁盘／飞书错误。
删除原文后没有消息不会自动重建，新消息到达才创建新文档；不要删除隐藏锁文件或修改内部 HTML 标识。

## 5. Docker 最后验证与部署

先完成本地演示及真实群／私聊落盘验证，再做 Docker 构建检查。
生产部署机只拉取 GitHub Actions 发布镜像；当前工作树须先发布新版本，旧镜像不会自动获得本轮修改。

.env 设置 FEISHU_CONFIG_PATH=config/feishu.toml，挂载配置目录与数据目录：
MYSERVICE_CONFIG_DIR 对应 /app/config（只读），MYSERVICE_DATA_DIR 对应 /app/data（可写）。
默认 SQLite 位于 /app/data/feishu/state.sqlite3，原文也须在数据挂载里。
如果已有 SQLite URL 写了开发机 /Users/...，部署时移除覆盖或改为容器路径，不能直接原样使用。
本模块不依赖业务 PostgreSQL、Alembic 迁移或 API 服务；其他业务仍按原部署方案运行。

```bash
# 静态校验，无需运行 Docker daemon
docker compose --profile inspiration config --quiet
# 已发布新版本后，单独启动采集；无业务库依赖
docker compose pull feishu-inspiration
docker compose up -d --wait feishu-inspiration
# 容器里查询，不再启动第二条长连接
docker compose exec feishu-inspiration python -m app.feishu_cli sources
docker compose exec feishu-inspiration python -m app.feishu_cli logs --role collector --lines 100
```

外部 PostgreSQL Compose 增加 -f docker-compose.external-postgres.yml，采集仍使用自身本地 SQLite。
日志驱动 none 避免额外 Docker stdout 积累，用正式文件日志查询。
仅改 TOML／路由时不重建镜像；仅改 .env 时用
`docker compose up -d --no-deps --force-recreate feishu-inspiration`。
代码修改先发布、拉取新镜像再重新创建采集容器，不影响其他运行角色。

如果以前启用过旧 AI 容器，须先停止它。新 Compose 已移除 inspiration-processing 服务，
可以用旧 Compose 配置停止该服务，或在管理界面停止旧容器；不要对整个项目执行 down --volumes。
确认旧 AI 角色已停止后，新配置只运行采集。旧原文、结果、状态库和备份均保留。

## 6. 验收与常见问题

| 场景 | 预期／处理 |
|---|---|
| 群聊／私聊发文本 | 指定文档包含完整时间、来源和原文；保存后收到 OK |
| 重启／重放相同事件 | 不重复追加；本地演示可验证 |
| 改一个群的 routes | 校验及热加载后，新消息写到新目标，旧文档保持原样 |
| 删除文档后发新消息 | 创建新文档，只有新内容，不恢复旧记录 |
| FeishuError | 查看安全 error_code，尤其检查凭证变量引用与飞书回执日志 |
| collection_state_error | 检查 SQLite 文件／目录写权限及磁盘，不迁移 PostgreSQL 来修复 |
| config.rejected | 旧版本继续运行；删除残留 AI 段，校验目标引用或重启 runtime 改动 |
| BlockingIOError | 同角色已有进程持锁；停止重复启动，不删除使用中的锁文件 |
| worker／process／retry 无效 | 这些 AI 命令已移除；仅使用 collect、sources、status、discover、logs、simulate |
| 没有立即 AI 回复 | 当前机器人只收录，不调用 AI；总结及交互 agent 后续独立设计 |


## 7. 现有容器更新清单

采集复用后端镜像，独立启动一个 feishu-inspiration 容器。FastAPI 容器不建立飞书长连接。
现有 data 挂载继续使用，只需增加 config 目录挂载；SQLite 与模块日志都在 data 内，不需第三个挂载。
不要把配置或数据复制进镜像。部署时提供真实 config/feishu.toml；Git 只发布示例，不包含私有配置。

| 宿主机内容 | 容器路径 | 权限与用途 |
|---|---|---|
| MYSERVICE_CONFIG_DIR，例如 /srv/myservice/config | /app/config | 只读；包含 feishu.toml |
| MYSERVICE_DATA_DIR，例如 /srv/myservice/data | /app/data | 可写；原文、SQLite、日志及锁文件 |
| data/my-inspiration/pending.md | /app/data/my-inspiration/pending.md | 当前 TOML 的文档目标，不需额外文件挂载 |
| data/feishu/state.sqlite3 | /app/data/feishu/state.sqlite3 | 默认内部来源与去重状态库，启动自动创建 |
| data/logs/feishu | /app/data/logs/feishu | 正式限量文件日志，使用 CLI logs 查看 |

挂载目录必须预先存在，data 必须能被容器运行用户写入。建议把 state_path 和 input_path 保持为
相对路径；runtime.root_dir=".." 在 /app/config/feishu.toml 中解析为 /app。状态库使用本机磁盘，
不要把 SQLite 放在 SMB／NFS 等不能保证锁语义的共享目录上。

部署机 .env 示例（仅调整部署机配置，不要覆盖开发机 .env）：

```dotenv
FEISHU_CONFIG_PATH=/app/config/feishu.toml
MYSERVICE_CONFIG_DIR=/srv/myservice/config
MYSERVICE_DATA_DIR=/srv/myservice/data
FEISHU_STATE_DATABASE_URL=
FEISHU_APP_ID=你的应用ID
FEISHU_APP_SECRET=你的应用密钥
```

FEISHU_STATE_DATABASE_URL 留空，默认使用 TOML 的 state_path。若已有 SQLite 文件位于
挂载目录下的其他位置，可显式使用例如 sqlite:////app/data/feishu-dev/state.sqlite3。
开发机的 sqlite:////Users/... 不能直接用于 Docker。没有额外 AI 参数、提示词挂载或整理容器。

### 7.1 同一部署机器更新

1. 确认当前 data 的真实宿主机目录，继续挂载它；不要换成新的空目录。
2. 停止旧采集，备份该 data 目录和私有 TOML。不要复制仍有写入的 SQLite，避免不一致。
3. 更新 Compose；准备 config/feishu.toml 并调整部署机 .env。旧 AI 整理进程／容器若存在，单独停用。
4. 等待新提交的 GitHub Actions 成功发布，再拉取并重新创建采集。仅 restart 不会换镜像或挂载。

内置数据库 Compose：

```bash
docker compose --profile inspiration config --quiet
docker compose pull feishu-inspiration
docker compose up -d --no-deps --force-recreate feishu-inspiration
```

外部数据库 Compose（每个命令都使用同一文件；沿用部署时原有项目名）：

```bash
docker compose -f docker-compose.external-postgres.yml --profile inspiration config --quiet
docker compose -f docker-compose.external-postgres.yml pull feishu-inspiration
docker compose -f docker-compose.external-postgres.yml up -d --no-deps --force-recreate feishu-inspiration
```

只更新采集不需要重建 API、前端、Notion 或数据库，也不需要执行 PostgreSQL 迁移。
本仓库保留的历史兼容迁移仍在 Alembic 历史中；若另外更新整个后端栈，按原方案备份和迁移业务库。
不要运行 down --volumes 或对整个项目使用 --remove-orphans 来替代针对旧整理角色的停用。

### 7.2 从开发机迁移到容器／另一台机器

数据库保存了消息去重 ID，也保存了原目标的绝对路径和文件身份；不能只复制 pending.md，
也不能假定复制 SQLite 后所有待写入任务会自动改为 /app/data 路径。

- 先在源端 status 确认 pending_messages、pending_receipts、failed_messages、failed_receipts 均为 0。
- 停止源端采集，备份并一起迁移 Markdown 与完整 SQLite；整个 data 目录复制时保留隐藏文件。
- 在目标端配置容器路径，指向迁移后的同一个状态库。历史去重 ID 继续生效，已写入原文保留。
- 宿主机路径变化后，新消息会创建使用新路径的文档状态，历史目标条目保留；这是正常现象。
- 如果源端仍有待写入或失败项，先处理完再迁移；不要带着旧绝对路径的积压任务直接启动容器。
- 不要让开发机和容器同时连接同一个机器人；不同机器的角色锁不能互相保护。

### 7.3 升级后验收

```bash
docker compose ps feishu-inspiration
docker compose exec feishu-inspiration python -m app.feishu_cli validate
docker compose exec feishu-inspiration python -m app.feishu_cli status
docker compose exec feishu-inspiration python -m app.feishu_cli sources
docker compose exec feishu-inspiration python -m app.feishu_cli logs --role collector --lines 100
```

使用外部数据库 Compose 时给每条命令加 -f docker-compose.external-postgres.yml。
在飞书发一条新文本，确认宿主机原文追加、收到 OK、没有持续错误；重启采集后再发一条验证。
logging.driver=none 下 docker logs 没有模块日志是预期行为，使用上面的 CLI 查询。
worker 健康检查禁用了镜像内仅面向 HTTP 的探针；容器 running 不等于飞书已连接，须结合文件日志和实际落盘验收。


容器启动后立即退出时，docker exec 无法使用。可运行一次仅校验配置的临时容器，不建立长连接：

```bash
docker compose run --rm --no-deps feishu-inspiration python -m app.feishu_cli validate
docker compose run --rm --no-deps feishu-inspiration python -m app.feishu_cli logs --role collector --lines 100
```

同样沿用实际部署的 -f／-p 参数。此处不要用 collect 作为排查命令，避免与仍在运行的实例重复连接。
