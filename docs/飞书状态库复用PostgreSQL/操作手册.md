# 飞书使用项目 PostgreSQL 操作手册

## 1. 推荐配置

config/feishu.toml：

```toml
[runtime]
root_dir = ".."
state_backend = "postgresql"
database_url_env = "FEISHU_STATE_DATABASE_URL"
```

.env：

```dotenv
FEISHU_CONFIG_PATH=config/feishu.toml
FEISHU_STATE_DATABASE_URL=
# 使用项目已有的 POSTGRES_USER／PASSWORD／DB／HOST／PORT，无需再填一份 URL。
```

database_url_env 填变量名，不填 URL，也不要填 POSTGRES_HOST。变量留空就复用项目 PG。
state_path 只在显式 SQLite 模式有作用，不需要删除，但 PG 不使用这个文件。
如果 .env 还保留 SQLite URL，它会优先覆盖默认 PG；切换时必须清空该值。
修改状态库配置或 .env 后需停止并重新启动采集，不热切换连接。

## 2. 本地建表与启动

本轮此开发环境已备份、迁移、导入旧状态，不需要手工建表。新环境执行：

```bash
uv sync --locked
# 先完成项目 PG 备份，检查当前迁移版本。
uv run alembic current
# 只有空库缺少历史 users 基表时，baseline 会创建它；既有表保持不变。
uv run python -m app.db.migration_baseline
uv run alembic upgrade head
uv run python -m app.feishu_cli validate
uv run python -m app.feishu_cli status
uv run python -m app.feishu_cli collect
```

baseline 和 Alembic 自动读取项目 .env，已 export 的变量优先。
项目历史迁移工具兼容 DATABASE_URL 覆盖；若使用它，确保与采集的 POSTGRES_* 或显式连接串指向同一库。
独立 PG 覆盖不会被 migrate 自动识别：独立库必须按项目迁移工具的 DATABASE_URL 指向正确目标。
缺表／缺列报 state_schema_missing，先检查迁移库是否一致，不能运行 init-local 修复 PG。
不要 drop 表、重置版本、无核对地 stamp，也不要让 worker 自动 create_all。

## 3. 旧 SQLite 去重状态导入

先让原 SQLite 采集处理完消息和回执；在旧配置下 status 的四项待处理／失败计数均须为 0。
停止原采集，备份原文和 SQLite。修改 .env 为 PG，并完成 PG 备份与 Alembic 迁移，再执行：

```bash
uv run python -m app.feishu_cli import-sqlite --source /旧状态库的绝对路径/state.sqlite3
uv run python -m app.feishu_cli status
```

导入输出每张表 inserted／skipped；源库只读，原文不改写，重复导入不会覆盖 PG 中已存在的状态。
启动正式采集后再测试。目录锁不能保护另一台机器，所有原实例都应先停用。
若旧库有积压或失败项，命令拒绝导入；回到旧环境处理后重试。
原路径随旧状态保存，迁往 Docker 时新消息创建对应容器路径的目标，旧目标保留作历史记录。
旧 feishu_runs 不导入，仍保存在原库和备份中。

显式 SQLite 仅用于兼容或隔离演示：

```toml
[runtime]
state_backend = "sqlite"
state_path = "data/feishu/state.sqlite3"
```

`uv run python scripts/feishu_local_demo.py` 会自行使用临时 SQLite 与本机 HTTP 替身，完全不连接项目 PG。

## 4. Docker 更新

挂载保持两处：

| 宿主机目录 | 容器目录 | 权限 |
|---|---|---|
| 包含真实 feishu.toml 的 config | /app/config | 只读 |
| 原文和模块日志的 data | /app/data | 可写 |

部署机 FEISHU_CONFIG_PATH=/app/config/feishu.toml，FEISHU_STATE_DATABASE_URL 留空。
内置 PG Compose 自动设置 db:5432；外部 PG Compose 使用项目 .env 里的现有连接参数。
两个方案均等待 migrate 成功后启动采集。PG 本身继续按原项目方式持久化和备份。

准备好新镜像后，先停旧采集并备份业务 PG 和文件，再执行内置方案：

```bash
docker compose --profile inspiration config --quiet
docker compose pull migrate feishu-inspiration
# 显式重新创建迁移容器，避免复用旧的已退出迁移任务。
docker compose up --no-deps --force-recreate --exit-code-from migrate migrate
# 迁移成功后更新采集；此处已完成迁移，不启动其他角色。
docker compose up -d --no-deps --force-recreate feishu-inspiration
docker compose exec feishu-inspiration python -m app.feishu_cli status
docker compose exec feishu-inspiration python -m app.feishu_cli logs --role collector --lines 100
```

内置数据库 db 必须已经启动且健康。已有项目更新不需要重建数据库、API 或前端。
首次启用整个项目按根 README 的流程，不要在 db 尚未就绪时使用这里的 --no-deps。
外部方案每条命令都增加 -f docker-compose.external-postgres.yml，并沿用现有 -p 项目名。
普通 restart 不更新镜像、挂载或 env_file；不要执行 down --volumes。

Docker 中导入已挂载的旧 SQLite：采集保持停止，运行单次命令，不启动长连接：

```bash
docker compose run --rm --no-deps feishu-inspiration python -m app.feishu_cli import-sqlite --source /app/data/旧目录/state.sqlite3
```

## 5. 验证边界

- 单元测试不连接真实 PG；覆盖配置优先级、特殊密码、PG 事务、缺表提示、SQLite 兼容与导入保护。
- 纯采集本地演示仍使用临时 SQLite 和 HTTP 替身。
- `tests/functional/test_feishu_postgres.py` 只使用统一入口创建的一次性 PG，验证采集恢复和导入；通过 `./scripts/test.sh functional` 执行。
- 不向项目实际 PG 写入合成测试数据。实际切换核对备份、迁移版本、来源／消息数量和原文不变。
- 真实飞书验收：重新启动采集，发一条文本，确认原文追加及 OK 回执；status 四项积压／失败计数为 0。
